## 本提交完成内容

### 1. 断线清理新增池化武器残留态校验（B4 可观测性收口的最后一项）

- `GameFramework/ShooterGameMode.cpp` 的断线清理扫描新增 `DirtyPooledWeaponCount`：
  对每一件已归还池的 WeaponActor 校验「干净的可复用状态」——
  无 Owner、无 Instance 绑定、无行名、已隐藏、生命周期为 `InPool`；
  任一条件不成立即输出 Error 明细，并把 `DirtyPooled>0` 纳入 `AUTOMATION_TEST_FAILURE` 判定。
- 两条成功日志（`AUTOMATION_TEST_DISCONNECT_SUCCESS` / `AUTOMATION_TEST_EQUIP_CLEANUP_SUCCESS Kind=Disconnect`）
  同步输出 `PooledWeapons` 与 `DirtyPooled`，使「断线玩家的武器确实回到池、且不带残留身份」成为可审计事实。

### 2. 非池出生归还路径的低噪声修正

- `Weapons/ShooterWeapon.cpp` 的 `OnOwnerDestroyed` 增加 `IsManaged` 前置判定：
  非池出生（NPC / 测试直接 Spawn）是受支持的兼容路径，不再触发对象池的 fail closed 警告。
  实测该路径在真实游戏世界中确实会被走到（角色销毁 → 拥有者销毁通知 → 归还边界），
  修正后五个网络阶段日志中的 `ActorPool Release rejected` 噪声归零。

### 3. 文档状态同步

- 最终路线规划第 15 节：当前状态由「待执行收口回归」改为「大阶段 B 收口回归已通过 → 待正式架构验收 → P1」。

### 验证边界（明确记录，不含糊）

- 「后续 Acquire 同一池化 Actor 时没有残留状态」在网络层面的证据是
  **池化 Actor 的干净性**（`DirtyPooled=0`：无 Owner / 无绑定 / 无行名 / 隐藏 / `InPool`），
  以及池化归还-复用计数闭环；
  **跨玩家经 Pickup 重新 Acquire 同一实例**这一具体路径由 Editor 自动化
  `ShootGame.Pool.WeaponGrant.AcquireBindsAndReuses` 覆盖（同一实例复用、重绑新 InstanceId /
  行名 / Owner / 弹药、可再次装备），现有网络协调器流程不会在死亡后重新授予生产武器，
  因此未在该层重复实现该场景。

## 遇到的问题

1. `OnOwnerDestroyed` 的非池出生回退会输出 `ActorPool Release rejected` 警告（每场景 2 条）：
   功能正确（fail closed 后回落销毁），但属 B4 要求清理的诊断噪声。

## 处理方式

1. 在 `OnOwnerDestroyed` 中增加 `IsManaged` 前置判定，与 `Inventory.ReleaseWeaponActor` 的既有判定一致；
   重新构建并复跑收口回归，五个阶段日志中的该警告归零，其余断言与标记不变。

## 遗留项

- **正式架构验收**（计划第 10 节）尚未由用户确认；冻结 `WeaponRowName / InstanceId / FireBehavior /
  WeaponActor Lifecycle` API 并进入 P1 的决定权在用户。
- NPC 兼容路径（直接 Spawn、无 WeaponInstance、`CurrentBullets` 镜像、不经池）按计划保留为明确的
  PvE 遗留项。
- 池化武器归还后仍是隐藏 Actor，未引入 Net Dormancy；Projectile 池、跨 World 池、
  动态容量回收算法仍为计划明确的非目标。
- 当前 Unreal Editor 实例仍在运行：构建因此产出分块模块 DLL（`UnrealEditor-ShootGame-0005.dll`），
  自动化与网络阶段均按 `.modules` 加载最新分块并全部通过；如需单一模块 DLL，可在编辑器关闭后重新构建。
