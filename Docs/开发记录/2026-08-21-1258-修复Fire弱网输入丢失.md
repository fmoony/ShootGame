# 修复 Fire 弱网输入丢失并验证换弹后单次开火

- 日期：2026-08-21
- 计划提交说明：`修复：Fire ServerOnly 客户端预检与换弹后单发弱网验证`
- 变更类型：生产代码 / 测试

## 目的

把上一提交对 GA_Reload 的弱网修复规则推广到 GA_Fire：服务器已结束 Reload、但客户端仍残留 `State.Reloading` 时，玩家单次按 Fire 不能被客户端本地预检吞掉。同时给 GA_Equip 壳体预置相同规则，并新增弱网网络测试：Reload 完成后客户端只提交一次 Fire，服务器只激活一次 GA_Fire、只生成一颗弹丸、只扣一发弹药。

## 根因

- 与 GA_Reload 相同：UE5.6 `UAbilitySystemComponent::TryActivateAbility` 对非权威端的 ServerOnly Ability 先调用 `Ability->CanActivateAbility`，返回 true 才发送 `ServerTryActivateAbility`。
- `UShooterGameplayAbility_Fire::CanActivateAbility` 原先先调用 `Super::CanActivateAbility`，Super 会读取客户端 `OwnedGameplayTags` 与 `ActivationBlockedTags`；弱网下 `State.Reloading` 移除复制迟到时，Fire 输入在客户端被拒，服务器永远收不到激活请求。
- GA_Fire 已配置 `ActivationBlockedTags` 包含 `State.Reloading` / `State.Equipping`，因此该窗口是真实生产风险。

## Epic 官方依据

- [EGameplayAbilityNetExecutionPolicy](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/GameplayAbilities/EGameplayAbilityNetExecutionPoli-?application_version=5.6)：ServerOnly Ability 客户端只提交激活请求，执行与最终校验在服务器。
- [UAbilitySystemComponent::ServerTryActivateAbility](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/GameplayAbilities/UAbilitySystemComponent/ServerTryActivateAbility?application_version=5.0)：客户端激活意图通过服务器 RPC 提交。
- [UGameplayAbility::CanActivateAbility](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/GameplayAbilities/Abilities/UGameplayAbility/CanActivateAbility?application_version=5.2)：该门禁在客户端与服务器都会调用；ServerOnly 场景应以服务器结果为最终裁决。

## 本地 UE5.6 源码核对结果

- `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/AbilitySystemComponent_Abilities.cpp`：
  - `TryActivateAbility` 非权威 + ServerOnly 分支：先 `CanActivateAbility`，成功才 `CallServerTryActivateAbility`，失败直接 `NotifyAbilityFailed`。
  - `ServerTryActivateAbility_Implementation` → `InternalServerTryActivateAbility` → `InternalTryActivateAbility`，服务器会再次调用 `CanActivateAbility`。
- `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/Abilities/GameplayAbility.cpp`：
  - 默认 `CanActivateAbility` 的 `DoesAbilitySatisfyTagRequirements` 读取客户端 `OwnedGameplayTags` 和 `ActivationBlockedTags`，这是延迟复制状态。
- 结论：GA_Fire 与 GA_Reload 一样，非权威客户端只做 ASC/Avatar 对应检查，Tag、Weapon、Ammo、Death 完整校验全部留在服务器。

## 生产代码修改

- `Source/ShootGame/AbilitySystem/Abilities/ShooterGameplayAbility_Fire.cpp`：
  - 非权威 Avatar 分支移到 `Super::CanActivateAbility` 之前；
  - 客户端只确认 `ActorInfo->AbilitySystemComponent` 存在且 `GetAvatarActor() == AvatarActor`；
  - 服务器端保持 `Super::CanActivateAbility` + 完整 Weapon / Ammo / Death 校验。
- `Source/ShootGame/AbilitySystem/Abilities/ShooterGameplayAbility_Equip.cpp`：
  - 壳体按相同规则重排，并注释明确 5C 正式实现时保持该顺序，Inventory / CurrentWeapon 完整校验放在服务器分支；未实现任何 Equip 业务逻辑。
- 未修改 ASC、Character、Inventory、GA_Reload；未恢复任何测试重试。

## 测试修改

- `ShooterNetworkTestCoordinator` 新增 Fire-after-Reload 弱网阶段，位于 TransferOnce 验证之后、EquipCancel 之前：
  - 服务器记录当前手枪弹匣与弹丸数，设置 `bServerReadyForFireAfterReload`；
  - 客户端只调用一次 `DoStartFiring()`，日志 `Fire-after-reload client input submitted once`，并只发送一次触发 RPC；
  - 服务器观测 `GetActiveAbilityCountForClass(Fire) == 1`、弹丸 +1、弹匣 -1；
  - 验证后服务器要求客户端只调用一次 `DoStopFiring()`；
  - 0.5 秒静默期后确认弹丸与弹药不再变化、无 `State.Firing`、无活动 Fire。
- 成功与超时标记新增 `FireAfterReload=ActiveObserved/SingleShot/Quiescent`，最终要求三项均为 true。

## 遇到的问题

- 编译期间两次头文件插入位置错误：`HasActiveFireAbility` 被插入到 `ReplaceInventoryWeaponForReloadTest` 参数列表中间；`bClientTriggeredFireAfterReload` 在客户端成员区与 5B 服务端观测区重复定义。

## 处理方式

- 检查 UHT/编译器指向的头文件行号，恢复函数参数声明顺序；删除重复成员，保留单份共享的 `bClientTriggeredFireAfterReload`（客户端本地置位 + 服务器 RPC 置位）。
- 给 `ShooterGameplayAbility_Equip.cpp` 增加 `AbilitySystemComponent.h` include。
- 修复后重新 Build，并通过全部单独网络阶段与最终完整 RunAll。

## 遗留项

- 与 GA_Reload 相同，客户端跳过 `Super::CanActivateAbility` 会让 Cooldown / Cost / 输入抑制等非法请求多发一次可靠 RPC，由服务器拒绝；当前规模可接受。
- GA_Equip 仍是壳体，5C 才接入 Inventory / CurrentWeapon 完整校验；本提交只预置客户端预检规则。
- 弱网测试覆盖 Reload 完成后单次 Fire，但尚未覆盖同帧 Fire/Reload/Death 并发、以及 PktLoss 更高或 PktLag 更极端的场景。
- 工作区中 `Source/ShootGame/AbilitySystem/ShooterAbilitySystemComponent.cpp` 的用户预留注释修改不属于本任务，保持未暂存。
