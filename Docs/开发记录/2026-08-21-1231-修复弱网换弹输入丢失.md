# 修复弱网换弹输入丢失

- 日期：2026-08-21
- 计划提交说明：`修复：避免弱网下换弹输入被残留标签吞掉`
- 变更类型：生产代码 / 测试

## 目的

修复 5B 遗留问题：服务器已结束上一轮 GA_Reload，但 `State.Reloading` 的移除复制尚未到达客户端时，玩家下一次按 R 会被 `GA_Reload::CanActivateAbility` 在客户端本地拒绝，`ServerTryActivateAbility` RPC 根本不会发出。目标是在保持服务器完整权威校验的前提下，让非权威客户端每次 R 只提交一次且必然到达服务器。

## 根因

- 本地 UE 5.6 调用链：
  - `UAbilitySystemComponent::TryActivateAbility`（`AbilitySystemComponent_Abilities.cpp` 约 1620-1660 行）对非权威端的 `ServerOnly` / `ServerInitiated` Ability，会先调用 `Ability->CanActivateAbility(...)`，只有返回 true 才调用 `CallServerTryActivateAbility` → `ServerTryActivateAbility`。
  - `UGameplayAbility::CanActivateAbility` 默认实现（`Abilities/GameplayAbility.cpp` 约 375 行）会执行 `CheckForBlocked(AbilitySystemComponent.GetOwnedGameplayTags(), ActivationBlockedTags)`。
  - 因此客户端本地残留的上一轮 `State.Reloading` 会在发送 RPC 前触发 `ActivationBlockedTags` 拒绝。
- 项目 `UShooterGameplayAbility_Reload::CanActivateAbility` 在 5B 中先调用 `Super::CanActivateAbility`，再检查非权威 Avatar；注释声称“客户端只检查 Avatar 存在”，实际行为与注释不一致。
- 5B 测试协调器当时用 0.25 秒 x 8 次重复 `DoReload` 绕过该问题，真实玩家单次 R 得不到这种重试，属于测试掩盖生产缺陷。

## Epic 官方依据

- [EGameplayAbilityNetExecutionPolicy](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/GameplayAbilities/EGameplayAbilityNetExecutionPoli-?application_version=5.6)：`ServerOnly` 表示 Ability 只在服务器执行，客户端输入应把激活请求提交给服务器。
- [UAbilitySystemComponent::ServerTryActivateAbility](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/GameplayAbilities/UAbilitySystemComponent/ServerTryActivateAbility?application_version=5.0) 与 [UAbilitySystemComponent::CallServerTryActivateAbility](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/GameplayAbilities/UAbilitySystemComponent/CallServerTryAct-?application_version=5.3)：确认客户端激活意图通过可靠服务器 RPC 提交，服务器再执行激活。
- [UGameplayAbility::CanActivateAbility](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/GameplayAbilities/Abilities/UGameplayAbility/CanActivateAbility?application_version=5.2)：`CanActivateAbility` 是客户端与服务器共用的激活门禁；本项目不能把客户端本地结果当作权威结果。
- 官方 API 页面没有直接给出“客户端预检应跳过 Super”的代码模板，因此本修复依据与本地 5.6 源码逐行核对后采取最小重排，并在开发记录中写明代价。

## 本地 UE5.6 源码核对结果

- `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/AbilitySystemComponent_Abilities.cpp`：
  - `TryActivateAbility` 非权威 + `ServerOnly` 分支：先 `Ability->CanActivateAbility`，成功才 `CallServerTryActivateAbility`，失败则 `NotifyAbilityFailed` 并返回 false。
  - `ServerTryActivateAbility_Implementation` → `InternalServerTryActivateAbility`：服务器重新进入 `InternalTryActivateAbility`。
  - `InternalTryActivateAbility` 再次调用 `AbilitySource->CanActivateAbility`；因此服务器会用自己的权威状态执行完整校验，客户端预检不会替代服务器校验。
- `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/Abilities/GameplayAbility.cpp`：
  - `UGameplayAbility::CanActivateAbility` 中 `DoesAbilitySatisfyTagRequirements` 读取 `AbilitySystemComponent.GetOwnedGameplayTags()` 与 `ActivationBlockedTags`；这是依赖复制状态的本地预检。
- 结论：对 `ServerOnly` Ability，客户端 `CanActivateAbility` 只需确保“请求确实来自当前 Avatar 的本地 ASC”，把 Tag / Cooldown / Cost / 业务校验全部留给服务器；服务器拒绝会通过 `ClientActivateAbilityFailed` 反馈。

## 生产代码修复方式

- 修改 `Source/ShootGame/AbilitySystem/Abilities/ShooterGameplayAbility_Reload.cpp` 的 `CanActivateAbility`：
  - 非权威 Avatar 分支提前到 `Super::CanActivateAbility` 之前；
  - 客户端只检查 `ActorInfo->AbilitySystemComponent` 存在且 `GetAvatarActor() == AvatarActor`，然后返回 true，让激活请求必然发出；
  - 权威端仍先调用 `Super::CanActivateAbility`，再调用 `ResolveReloadTarget` 完成完整权威校验。
- 代价说明：客户端不再本地拦截 Cooldown / Cost / 输入抑制 / 过期 Tag；这类非法请求会多发一次可靠 RPC，但由服务器拒绝。这是 ServerOnly 语义下换取单次输入不丢失的最小代价，不改变任何权威结果。
- 不修改 ASC、Character、Inventory、GA_Fire、GA_Equip；不引入循环重发输入。

## 为什么删除测试重试

- 重试掩盖了生产问题：只要有一次重试落在 Tag 移除复制之后，网络测试就会通过，真实玩家单次 R 仍会丢失。
- 修复生产代码后，客户端不再读取可能过期的 `ActivationBlockedTags`，单次输入即可稳定到达服务器；测试必须验证该事实，而不是继续制造额外的生产入口调用。
- 已删除 `PendingReloadPressCount`、`NextReloadPressTime` 两个测试成员，以及切枪时清零重试计数的代码。

## 测试端单次输入验证

- `ShooterNetworkTestCoordinator::PollClientState` 现在对每个新 `ReloadInputRequestId` 只调用一次 `Character->DoReload()`，并输出：
  `Reload client input submitted once: PlayerId=<ID> RequestId=<N>`
- 最终 EmulatedNetwork 日志中，每个客户端每个 RequestId 均只有一条该日志（`uniq -c` 全部为 1），服务器日志中每个 RequestId 只有一条对应 `Reload client report`。
- 服务器合法请求日志 `GA_Reload activated`、单次 `Inventory ReloadMagazine committed` 与最终 `Reload=true/true/true/true/true/true` 共同证明一次输入、一次激活、一次转移。
