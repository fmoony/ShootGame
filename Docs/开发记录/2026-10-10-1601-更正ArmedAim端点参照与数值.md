# 更正 ArmedAim 端点的参照与数值

- 日期：2026-10-10
- 计划提交说明：`文档：更正ArmedAim端点参照与数值`
- 变更类型：文档

## 目的

提交 `ca2976e` 的开发记录把端点表中的一行写成“ArmedAim ↔ `MM_Rifle_AimToLowReady` 首帧
39.196cm / 44.296cm / 48.0°”。该数值实际量的是**未叠加 AimOffset 的裸
`MF_Rifle_Idle_ADS` 第 0 帧**，不是 `ArmedAim` 的真实输出。
本提交只更正该结论的依据与数值，不改动任何资产或代码。

历史记录按仓库约定保留原貌，因此以本记录为准。

## 本提交完成内容

- 新增本记录，说明更正后的 `ArmedAim` 端点定义、重算数值与剩余不确定性。

## 验证结果

`ArmedAim` 的真实输出链路（由 `Saved/MCP/graph_anim_graph.json` 的引脚与
`FAnimNode_RotationOffsetBlendSpace::Evaluate_AnyThread` 确认）：

```text
ArmedAimPose = SequencePlayer(ThirdPersonHoldSequence = MF_Rifle_Idle_ADS)
               -> AimOffsetPlayer(ThirdPersonAimOffset = AO_Rifle, Y = AimPitchN)
               -> SaveCachedPose('ArmedAimPose')
```

`AimPitchN = sin(俯仰)`，范围 `[-1, 1]`（`ShooterThirdPersonAnimInstance.cpp:555-556`）。
`AO_Rifle` 只有 3 个样本，均为 `AAT_ROTATION_OFFSET_MESH_SPACE` + `ABPT_ANIM_FRAME`，
参考序列为 `MF_Rifle_Idle_ADS`，每个样本长 1 帧：

| AO 样本 | Y | 含义 |
| --- | --- | --- |
| `MM_Rifle_Idle_ADS_AO_CU` | +1 | 上仰 |
| `MM_Rifle_Idle_ADS_AO_CC` | 0 | 平视 |
| `MM_Rifle_Idle_ADS_AO_CD_Fixed` | -1 | 下俯 |

三个样本的姿态随 Y 单调合理（手部 z 约 166/196（上仰）、138/144（平视）、114/83（下俯）），
且平视样本最接近基准 Hold；据此认定经求值得到的样本姿态即 `ArmedAim` 在对应 `AimPitchN`
下的姿态。重算命令：

```text
UnrealEditor-Cmd <project> -run=PythonScript -Script=Saved/MCP/recompute_armedaim_joins.py
```

与 `MM_Rifle_AimToLowReady` 第 0 帧的差（手部组件空间距离 / 13 骨最大局部角差）：

| 参照 | 右手 | 左手 | 最大角差 | 平均角差 |
| --- | --- | --- | --- | --- |
| `ArmedAim` Y=+1（上仰） | 51.911cm | 97.029cm | 63.001° | 23.735° |
| `ArmedAim` Y=0（平视） | **26.132cm** | **42.704cm** | **52.564°** | 20.853° |
| `ArmedAim` Y=-1（下俯） | 36.559cm | 75.993cm | 69.027° | 24.453° |
| 裸 `MF_Rifle_Idle_ADS` 第 0 帧（此前误用） | 39.196cm | 44.296cm | 48.000° | 17.003° |

即：改用正确参照后右手差距由 39.196cm 降到 26.132cm，左手基本不变（44.296 → 42.704cm），
最大局部角差反而略增（48.0 → 52.564°）。**任何俯仰下的最好情况仍是 26cm 量级**，
因此“`ArmedAim` 端与 `MM_Rifle_AimToLowReady` 首帧差距过大、不能靠极短 Blend 掩盖”这一判断
在正确参照下依然成立，只是数值与依据需要替换。

## 遇到的问题

- 预审查原文写的是“首帧与**当前 Hold** 双手相差约 39.20 / 44.30cm”，
  我在端点表中把它改写成了“ArmedAim ↔ …”，丢掉了 `AimOffset` 这一层。
- 首次尝试手写合成时把乘法次序写反。`FTransform::AccumulateWithAdditiveScale`
  （`TransformNonVectorized.h`）是 `Rotation = Additive.Rotation * Base.Rotation`，
  增量在左侧；先写成 `Base * Additive` 后修正，但两组结果都不可用：
  修正次序后手部 z 达约 340cm，说明把 AO 样本读成了绝对姿态而非增量。
- Python 侧没有暴露 `IAnimationDataController`，也没有直接暴露
  “把加法姿态叠加到基准姿态”的接口，无法在脚本里可靠复现引擎的合成；
  最终改用“AO 样本的求值结果即合成后姿态”这一可交叉验证的口径。

## 处理方式

- 读本地 UE5.6 源码核对 `FAnimNode_RotationOffsetBlendSpace::Evaluate_AnyThread`、
  `AccumulateMeshSpaceRotationAdditiveToLocalPose`、`ConvertPoseToMeshRotation` 与
  `FTransform::AccumulateWithAdditiveScale` 的实际语义，不再凭推断。
- 读 `AO_Rifle` 的样本类型、基准姿态类型与参考序列，确认参考序列正是主图喂入的
  `MF_Rifle_Idle_ADS`，从而可以把它当作 `ArmedAim` 的可用参照。
- 用 `Saved/MCP/recompute_armedaim_joins.py` 重算并把结果写入本记录；
  工作区进度文档同步更正。

## 遗留项

- 仍有残余不确定性：`AO_Rifle` 的内部混合值未逐点覆盖，上表只取三个样本值；
  游戏内 Hold 序列在 8 秒内小幅变化，也未逐帧扫描。两者量级都远小于 26cm，不影响结论方向。
- `MM_Rifle_Holster` 首帧 ↔ `MM_Rifle_LowReady`（17.223cm / 9.541cm）与
  `MM_Rifle_Draw` 末帧 ↔ `MM_Rifle_LowReady` 两行未受影响，仍以 `ca2976e` 记录为准。
- 阶段 B 的门控结论不变：`ArmedAim` 端最好情况仍为 26cm 量级，未达到可接线质量。
