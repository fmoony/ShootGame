# 单发开火语义：一次 GA_Fire Activation 等于一发 Shot

- 日期：2026-10-06
- 计划提交说明：`重构：将开火语义收敛为一次 GA_Fire Activation 一发 Shot`
- 变更类型：生产代码 / 测试 / 文档

## 目的

当前一次 `GA_Fire` Activation 代表"一段持续开火"：客户端在 Ability 内用
`PredictedFeedbackTimer` 连续预测多发，服务器在 `AShooterWeapon` 内用 `RefireTimer`
连续提交多发，两端各自连续产生 Shot，只能在事后用"按 Activation 的预测账本 +
四槽结果环 + 每轮可靠最终 RPC + 确认补播队列"做发数对账。

本轮把射击动作统一为：

```text
一次 GA_Fire Activation = 一次 Shot
```

- Server 接受一次 Activation ⇔ 服务器真正提交且只提交一发 Shot；
- FullAuto 的连发语义改为"输入仍 Held → 本地节拍到期 → 再次激活一次 GA_Fire"；
- 每一发拥有独立的 Activation、PredictionKey、Accept / Reject 与表现生命周期。

目标是让 Client 与 Server 对"什么是一发射击"拥有同一个动作身份，
从而删除因为两端独立连续产生 Shot 而必需的整轮发数对账复杂度。

## 外部依据与本地实现现状

- Epic 官方 Lyra 文档（5.6）在 `ULyraGameplayAbility` 的 Activation Policy 一节说明：
  自动武器使用 `WhileInputActive` + `Retrigger Instanced Ability = false`，
  "播放开火蒙太奇 → 等 refire 时间过去 → 结束 Ability"，由框架逐帧重试维持连发；
  并明确警告 `WhileInputActive` 与 Retrigger 同时开启会 spam activation。
  本轮的"每发一次独立 Activation"与官方参考实现一致，但节奏控制改为
  "本地开火节拍 + ASC 输入解释层重试"，不复制 Lyra 的 Ability 结构。
- 本地 UE 5.6.1（CL 44394996）GAS 源码核对的关键事实：
  - `InternalTryActivateAbility` 先调用 `CanActivateAbility`（1796），
    本地失败**不发任何 RPC**，只广播本地失败委托（2531-2534）；
    因此"本地节拍未就绪"可以安全地每帧尝试，不构成网络成本。
    - LocalPredicted 分支先 `CallServerTryActivateAbility`（1933）再本地
    `CallActivateAbility`（1957），
    所以"服务器仍会独立裁决这一发"与"本地是否提前表现"互相独立。
  - 服务器 `ClientActivateAbilitySucceed` 在 `CallActivateAbility` **之前**发出（1882 vs 1901），
    它只证明"服务器开始执行这次 Activation"，不能当作"服务器已完成提交"。
  - `ClientActivateAbilitySucceed` 的实例匹配条件是
    `Instance->CurrentActivationInfo.GetActivationPredictionKey() == PredictionKey`（2397）：
    对 `InstancedPerActor` 而言，下一次本地激活会覆盖同一个实例的 `CurrentActivationInfo`，
    因此连发时前几发的 `OnConfirmDelegate` 不会广播。
    → 每发一确认**不能**依赖 `OnConfirmDelegate`。
  - `ClientActivateAbilityFailed` 是 `Client, Reliable`，并且在处理器最开头
    无条件 `FPredictionKeyDelegates::BroadcastRejectedDelegate`（2254-2257），
    与实例是否存活无关 → Reject 仍按 `PredictionKey` 的 Rejected 委托结清。
  - 引擎没有"激活成功之后再拒绝"的能力（`NotifyAbilityFailed` 不发 RPC）：
    判定必须全部放进 `CanActivateAbility`，这也是本轮把权威射速判据前移的原因。
  - `net.MaxRPCPerNetUpdate` 只限制 unreliable multicast，与 GAS 可靠激活 RPC 无关。

## 本提交完成内容

### 1. 服务器：单发提交成为唯一权威开火入口

  - `AShooterWeapon` 删除 `StartFiring` / `StopFiring` / `Fire` / `FireCooldownExpired` /
  `bIsFiring`，
  新增：
  - `CanCommitAuthorityShot()`：权威射速资格，`TimeOfLastShot + RefireRate` 之前不得再提交，
    半自动与全自动共用同一判据；带 15ms 抖动容差（不累积，持续射速不可能超过 RefireRate）。
  - `CommitSingleShot(int32 ActivationKey)`：**一次调用最多产生一发权威 Shot**，
    顺序为 权威扣弹 → 开火行为（弹丸 / Montage / Multicast FX / 后坐力）→ 记录射速时钟
    → 排下一次"节拍就绪"通知 → 向拥有端发送这一发的 Committed 裁决。
  - `TimeOfLastShot` 复位语义改为"小于 0 表示已就绪"；取用、归还、恢复初始弹药都会复位，
    世界启动初期与复用租用的第一发不会被冷却误挡。
- `RefireTimer` 保留但语义收窄为"权威节拍到期通知"：只回调 `HandleAuthorityRefireReady()`
  → `IShooterWeaponHolder::OnWeaponRefireReady()`，**不再产生任何 Shot**。
  NPC 连发由这条通知驱动（重新提交一次开火意图），玩家连发由输入层驱动。
- 删除整轮结果通道：`FShooterFireActivationResult`、四槽结果环、`ActivationSerial`、
  `ClientFireActivationSettled`、`BeginAuthorityFireActivation` / `RecordAuthorityShotCommitted` /
  `SettleAuthorityFireActivation`、`PublishAuthorityFireActivationResult`、
  `OnRep_FireActivationResults`、`ResetFireActivationResultState`。
  替换为每发一次的 `ClientShotCommitted(ActivationKey, Snapshot)`（`Client, Reliable`，
  只在拥有者是需要通知的远端玩家时发送）。
- 删除 `OnOutOfAmmo` 委托与对应 Ability 收口：一次 Activation 只提交一发，
  打空由"下一次 Activation 被弹药门槛拒绝"表达，不需要第二个结束路径。
- 删除确认补播队列 `PendingConfirmedFeedback` / `ConfirmedFeedbackTimer` /
  `NextConfirmedFeedbackTime` / `DrainOwnerConfirmedFeedback` / `CancelOwnerConfirmedFeedback`：
  一次 Activation 至多补播一次，节奏由"每发一次 Activation"自身提供。

### 2. GA_Fire：一次 Activation 一发 Shot

  - `ActivateAbility` 权威路径只做一件事：`Weapon->CommitSingleShot(ActivationInfo 的
  PredictionKey)`，
  随后立即 `EndAbility`（且 `bReplicateEndAbility = false`，不需要第二条结束 RPC）。
  完整校验全部前移到 `CanAuthorityStartFire`（Tag 门控 → Avatar / 死亡 / 武器归属 / 可见 / 有弹药
  → 全自动仍按住 → 权威射速），因此不会再有"接受 Activation 但最终没有开枪"的中间态。
- `ActivateAbility` 拥有端路径：一次 Activation 至多预测一发。
  - `CanLocallyStartFire` 现在对**两种模式**都要求本地开火节拍就绪；
    本地弹药预算刻意不参与门控——预算不足只代表这一次不提前表现，请求照旧到达服务器。
  - 本地节拍在每次提交 Shot Attempt 时都推进一次（无论是否提前表现），
    因此按住输入时请求频率恒为 1 / RefireRate，不会变成每帧一次的请求洪水。
  - 删除 Ability 内的 `PredictedFeedbackTimer` 连续预测循环
    （`StartOwnerFireLoop` / `HandleOwnerFireTick` / `StopOwnerFireLoop`）。
  - 按 `PredictionKey` 保留一条 **Shot 记录**（武器 + 预测代次 + 是否预测 + 是否抑制反馈 +
  是否结清）：
  它必须活过本地 Ability 的结束（本地一发结束得比裁决到达早一个 RTT），因此不能放在激活实例状态里。
- 裁决结清：
  - Committed（`ClientShotCommitted`）：预测过 → `ConfirmPredictedAmmo(1)` 并**不**重复播放；
    未预测 → `PlayOwnerConfirmedShotFeedback()` 补播恰好一次。
  - Rejected（引擎 `PredictionKey` Rejected 委托）：预测过 → `RefundPredictedAmmo(1)`；
    未预测 → 什么都不做。已播出的瞬时表现不回滚，也不补播。
  - 两条路径都幂等（`bResolved`），且都校验武器预测代次，旧武器 / 旧租用的迟到裁决不参与结清。
- `PredictedShotsThisActivation`、`FPredictedFireActivationLedger` 的全部多发字段
  （`ProcessedSeen` / `BackfilledShots` / `ReconciledPredictedShots` / `HighestBackfilledOrdinal` /
  `NextLocalAttemptOrdinal` / `SuppressedShots` / `ActivationSerial` / `bServerConfirmed`）、
  `EShooterOwnerShotAttemptDecision`、`DecideOwnerShotAttempt`、
  `DiscardPhantomPredictedAmmo` 全部删除。
- 输入层不改：`UShooterAbilitySystemComponent::ProcessAbilityInput` 的
  `WhileInputActive` 分支本来就是"未激活且仍按住时每个输入帧尝试一次"，
  现在由 `CanLocallyStartFire` 的本地节拍把它节流成 1 / RefireRate。

### 3. HUD 与弹药职责

- `MagazineAmmo` / `ReserveAmmo` 仍是服务器权威，客户端不改真实弹药。
- `PendingPredictedShots` 语义收窄为"已经提前预测、但裁决尚未回来的一发的本地预算"：
  只由 Committed / Rejected 裁决结清（不再由弹药数值差吸收——文档 2026-10-05 的 H-A1 已证明
  "射击与换弹在同一复制帧互相抵消"时数值差不可用）。
- `OnRep_MagazineAmmo` 恢复为纯展示推送：不推断"确认了几发"。
- `FShooterAmmoDisplayState` 的显示协议保持不变（基线快照 + Revision + 延迟快照），
  但每轮显示扣减固定为 ≤1 发，结清由每发裁决携带的显示快照完成。

### 4. 生命周期

- 换枪 / 收起 / 清空装备不再调用已删除的 `StopFiring`：一次 Activation 只提交一发并立即结束，
  旧武器靠 `State.Equipping` / `CancelAbilitiesWithTag(Input_Fire)` 与表现收敛收口。
- NPC 死亡额外清掉"还想射击"的意图（`bIsShooting = false`），
  迟到的权威节拍通知不得再提交新的开火请求。
- `IShooterWeaponHolder::OnSemiWeaponRefire` 改名为 `OnWeaponRefireReady`（两种模式共用）。

## 按契约标题含义的不变量覆盖确认

```text
Invariant 1 Owner Immediate Feedback
- 含义中本次改动触及的维度：本地动作边界（本地 Shot Attempt）、表现来源、无单向缺口。
- 含义中本次改动不应改变的维度：拥有者第一人称表现仍只由本地预测 / 确认补播产生，
  远端表现仍只来自服务器确认。
- 需要的新增证据：本地预测一发的表现次数（客户端）；未预测但被服务器接受的那一发补播恰好一次；
  服务器已提交但拥有端从未表现的缺口必须为 0（网络夹具按发比对）。
- 明确不在本次范围的维度与理由：Projectile 与命中表现仍属服务器权威，不在本地预测范围。

Invariant 2 Local Prediction Obeys Weapon Rules
- 含义中本次改动触及的维度：服从（本地节拍与武器有效性）、不越权（不预测 Ammo / Projectile）、
  收敛（Reject 后预算与表现收敛）。
- 含义中本次改动不应改变的维度：本地预测仍不写 Ammo / 不生成弹丸 / 不结算伤害；
  仍不用可能过期的复制状态二次否决已经成立的动作边界。
- 需要的新增证据：请求节流（按住时请求数 ≈ 1 / RefireRate）、
  本地预算为 0 时仍产生服务器请求、Reject 恰好退款一次。
- 明确不在本次范围的维度与理由：本地不再预测换弹弹药转移（沿用服务器权威）。

Invariant 3 Server Is Final Authority
- 含义中本次改动触及的维度：动作已提交校验、结果只由服务器产生、拒绝无结果且客户端收敛。
- 含义中本次改动不应改变的维度：Ammo / Reload / Projectile / Hit / Damage / Death 仍只由服务器产生。
- 需要的新增证据：Accepted Activation 数 == Authority Shot 数（每发一一对应）；
  权威射速不足时 Activation 失败且权威发数不增加；Reject 不产生任何权威结果。
- 明确不在本次范围的维度与理由：不引入客户端命中信任。

Invariant 4 Remote Is Confirmed Only
- 含义中本次改动触及的维度：远端表现来源仍必须是服务器确认。
- 含义中本次改动不应改变的维度：Multicast FX 与第三人称 Montage 的产生位置不变。
- 需要的新增证据：远端确认表现次数随权威发数增长，且不因本地预测路径翻倍。
- 明确不在本次范围的维度与理由：远端纯表现仍不承诺逐发必达。

Invariant 5 Exactly One Authority Result
- 含义中本次改动触及的维度：一次被认可的 Gameplay 动作只产生一份权威结果；
  Owner 对同一动作只看到一次表现。
- 含义中本次改动不应改变的维度：不产生双扣弹 / 双弹丸 / 双伤害。
- 需要的新增证据：单次 Activation 的权威发数恒为 0 或 1（不存在一轮多发的路径）；
  预测 + 接受时拥有端总表现次数为 1；预测 + 拒绝时退款一次且不补播。
- 明确不在本次范围的维度与理由：换弹事务的"恰好一次"仍由 GA_Reload 覆盖。
```

## 遇到的问题

1. 新增的权威射速测试写入器与"从未开火"哨兵冲突：`SetAuthorityRefireRemainingForAutomationTest`
   在世界时间 ≈ 0 的 Editor 测试世界里会把 `TimeOfLastShot` 写成负数，
   而当时 `CanCommitAuthorityShot()` 用 `TimeOfLastShot < 0` 表示"已就绪"，于是三个断言失败
   （`AuthorityRefireGate` 两条、`LocalFireCadence` 一条）。
2. Emulated（`-PktLag=100`）首轮会话失败：`AUTOMATION_TEST_FAILURE: Ammo prediction ReloadLifecycle
   never observed a server-side reload window`（会话 `20261006_122509`）。日志显示服务器在
   `Step=6` 起始后 1.16 秒就判定了"前提构造失败"，而客户端日志里这次 Hold 直到 0.4 秒之后才开始：
   Hold 指令、Reload 输入与松手都是可靠 RPC，100ms 延迟下服务器先看到的是"弹匣满 + 无换弹"。
3. `RunNetworkSession.ps1 -ServerExtraArgs @('...')` 不能通过 `pwsh -File` 传数组：
   `-File` 把 `-ShootGameAmmoPredictionTest` 当成脚本参数解析并报"找不到与参数名称匹配的参数"。
4. 网络夹具在复核时发现：`FPredictedShotRecord` 的单一 `bPredicted` 同时承担
   "已消费预算"与"已播表现"两件事；表现通道失败时预算会被标记为未预测，裁决到达后既不结清也不退还。

## 处理方式

1. 把"从未开火"从特例分支改成哨兵时间 `NeverFiredShotTime = -1000000.0f`：
   射速判据只做 `Elapsed + 容差 >= RefireRate`，不再有 `< 0` 分支，
   近零但为负的测试时间也被正确当作真实的过去时刻。
2. 给 Reload 用例的前提判定加迟到窗口：
   `AmmoPredictionHoldStartTime + HoldSeconds + ReloadDuration + 2.0s` 之内只等待，
   超过才判前提失败；并显式记录该用例的 Hold 指令下发时间。
3. 改用 `pwsh -Command "& '<script>' -ServerExtraArgs @(...)"` 调用脚本（同一脚本、同一语义）。
4. 拆成两个独立事实：`bBudgetConsumed`（决定 Committed 结清 / Rejected 退款）与
   `bFeedbackPlayed`（决定 Committed 是否需要补播），并补一个 Automation 用例覆盖
   "预算已消费但表现未播出"的 Committed 与 Rejected 两个方向。

## 遗留项

1. **900 RPM 在低客户端帧率下的达成射速**：无延迟 Dedicated 会话里 900 RPM 只达成
   13.798/s（-8.0%），45 次请求里 3 次被权威射速拒绝。逐间隔数据
   （Min 65.6ms / Max 133.5ms）表明本地节拍被客户端输入帧量化，
   而服务器侧固定 15ms 容差覆盖不了这种量化。当前选择是保留固定容差并如实记录；
   若要求高射速在低帧率下仍精确，需要把容差改成"按请求方帧时间派生的有界允许量"
   （需要新的设计确认）。
2. 夹具的 `SemiAutoSingleShot` 跑在正式 Rifle（**全自动**）上，只证明
   "一次按下沿 → 一次 Activation → 一发"，不覆盖半自动 `OnInputTriggered` 策略分支；
   夹具运行时输出
   `AMMO_PREDICTION_EVIDENCE_GAP Case=SemiAutoSingleShot Reason=WeaponIsFullAuto`
   显式声明该缺口，该分支当前只由 Ability 层 Automation 覆盖。
3. **每发的拥有端确认不能使用 `OnConfirmDelegate`**：本地 UE 5.6.1 源码确认
   `ClientActivateAbilitySucceed` 按 `Instance->CurrentActivationInfo` 的 PredictionKey
   匹配实例（`AbilitySystemComponent_Abilities.cpp:2397`），而 `InstancedPerActor`
   的下一次本地激活会覆盖同一实例的 `CurrentActivationInfo`；连发（RTT 大于节拍）时
   前几发拿不到确认委托。因此确认走武器侧
   `ClientShotCommitted`，拒绝仍走引擎 `ClientActivateAbilityFailed` 的 Rejected 委托
   （`PredictedRejected` 用例的 `ByEngine=1` 证明该通道在真实运行中确实送达）。
4. 未结清的 Shot 记录不设容量淘汰与超时重同步（沿用原账本的既有边界）；
   `ResetAmmoPrediction`（Owner 变化 / 归还池 / teardown）是唯一的强制清理点。
5. `State.Firing` 现在是"一次性"的激活标签（同一帧内挂载与移除）。生产代码没有读取者，
   `UShooterAnimInstanceBase::bIsFiring` 因此恒为 false；本次未删除该字段与其数据契约测试，
   但后续若要表达"正在开火"的表现必须另找来源（例如 Montage 状态），不能再依赖该 Tag。
6. 远端第三人称表现仍按发触发（Multicast FX / Montage 各一发），成本与改造前相同；
   本改造没有承诺远端纯表现的逐发必达。
7. 本提交尚未执行 `git add` / `git commit`；提交前需按规范暂存并再次运行版式与包含路径检查。
