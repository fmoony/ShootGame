# 收敛 ASC 输入意图职责并统一 Held 语义

- 日期：2026-09-18
- 计划提交说明：`重构：按输入意图边界收敛 ASC 职责并统一 Held 语义`
- 变更类型：生产代码 / 测试 / 文档

## 目的

输入缓冲与换弹本地预测（`8b61dde` / `25e274e` / `d7d52da`）在实现过程中
积累了不属于「通用输入意图」的职责，以及只服务当时 workaround 的状态。
本提交做一次纯减法收敛：

- ASC 只负责 Press / Release / Held / 短期 Buffered Press /
  短暂阻塞解除后的一次重试；
- 删除「按住型输入」的能力侧虚函数与整套定时重试链；
- Fire 与 Reload 的关系只通过 GAS Tag 表达；
- 旧输入绝不跨死亡 / 重生 / Avatar 变化被消费。

不新增任何 Gameplay 功能，不做 Ammo / Projectile 预测，不新增状态机或 Retry Timer。
生产代码净减 70 行（新增 199 / 删除 269，其中 ASC 自身净减 96 行）。

## 本提交完成内容

### 1. 输入语义：Ability 虚函数 → Spec 行为标签

- 新增原生标签 `InputBehavior.HeldRepeat`
  （`ShooterGameplayTags.h/.cpp`），语义：
  「`Spec.InputPressed` 仍为 true 时，短暂阻塞解除后允许该 Spec 重新尝试激活」。
- 删除 `UShooterGameplayAbility::IsSustainedInputAbility()` 与 GA_Fire 的 override。
  GA_Fire 同时服务 Semi 与 FullAuto，行为标签不能固化在 Ability 上。
- 标签写在 `FGameplayAbilitySpec::DynamicSpecSourceTags`
  （引擎标注为随 Spec 复制），由 ASC 新增的生产 API
  `SetHeldRepeatInputBehavior(InputTag, bEnabled)` 幂等写入并标脏。

### 2. 标签同步入口：装备收敛（集中实现，无 Tick）

- `UShooterEquipmentComponent::SyncFireHeldRepeatInputBehavior(Weapon)`
  是唯一实现：按 `Weapon->IsFullAuto()` 决定 Fire Spec 是否带该标签。
- 两个调用点都在同一个类、同一套「当前武器」收敛语义内：
  - `BroadcastEquippedWeaponChanged`：服务器 `EquipWeapon` 提交 /
    `ClearEquippedWeapon` / 客户端 `OnRep_CurrentWeaponActor` 都经过它；
  - `HandleWeaponActorReady`：WeaponActor 的 Owner / WeaponId / 行配置晚到时补做
    （`OnRep_WeaponId` 会先 `ApplyWeaponRow` 再回调，因此读到的是新武器的连发语义）。
- 服务器与拥有者客户端各自按自己看到的 `CurrentWeaponActor` 收敛；
  客户端 Spec 复制到达时会带着服务器已同步好的标签，复制晚于装备也不会丢语义。
  没有 Tick 更新，没有新增状态机。

### 3. 删除定时重试链，只保留一次安全重试

- 删除 `MaxHeldRetryPerPress` / `HeldRetryIntervalSeconds` /
  `HeldRetryTimer` / `HeldReArmAttempts` / `ScheduleHeldRetryCheck` /
  `HandleHeldRetryCheck` / `TryReArmSustainedInput` / `ReArmSustainedInputs` /
  `ClearHeldRetryTimer` 与 `GetHeldReArmAttemptsForTest`。
- `ProcessBufferedInputs()` 成为唯一的安全时点入口：先消费未过期条目
  （每个条目最多一次），再对「仍按住 + 带 HeldRepeat 标签 + 未激活」的
  Spec 尝试一次 `RetryHeldRepeatInputs()`。被拒不会排程下一次，
  下一次机会只来自新的短暂阻塞解除事件，因此不存在 Server Reject → Retry 循环。

### 4. Fire / Reload 关系只通过 Tag

- GA_Reload 与 GA_Equip 的命令式 `CancelAbilitiesByTag` 改为构造函数里的
  `CancelAbilitiesWithTag`，由引擎在 `UGameplayAbility::PreActivate` 按
  AssetTags 执行（`GameplayAbility.cpp:985` → `ApplyAbilityBlockAndCancelTags`
  → `CancelAbilities(..., Ignore=this)`）。
- 两个 Ability 因此删除了
  `#include "AbilitySystem/ShooterAbilitySystemComponent.h"`
  与该处对项目 ASC 的唯一直接依赖。
- 时序等价依据：`PreActivate` 先挂 `ActivationOwnedTags`
  （`GameplayAbility.cpp:963`）再执行取消，与原先在 `ActivateAbility` 内取消一致；
  权威 `CanActivateAbility` 被拒的换弹 / 换装不进 `PreActivate`，不会多取消事务；
  `EndAbility` 只解除 Block 不重复取消（`GameplayAbility.cpp:868`）。

### 5. 生命周期：显式死亡清理取代 Fatal watcher

- 删除 `FatalInputBlockedTags`、`HandleFatalBlockedTagChanged` 与对应 Tag 监听表。
  `State.Dead` 本就不在 `TransientInputBlockedTags` 中，
  失败分类已使它无法进入缓冲。
- `ClearBufferedInputs()` 提升为公开 API，由宿主在明确边界调用：
  `AShooterCharacter::ApplyDeathState()`
  （服务器 `Die()` 与客户端 `OnRep_IsDead` 共用入口）。
- `InitAbilityActorInfo` / `ClearActorInfo` / `EndPlay` 继续由 ASC 自行清理。
- NPC 不参与输入缓冲
  （`FGameplayAbilityActorInfo::IsLocallyControlledPlayer()` 对 AI 控制的 Pawn
  恒为 false），因此 NPC 死亡沿用既有取消链即可。

### 6. 其他减法

- 删除只写不读的 `bOwnerFeedbackPlayedThisActivation`（GA_Fire）。
- 删除无调用者的测试钩子 `HasBufferedInputForTest`。
- 条目表由 `TArray` + 扫描改为
  `TMap<FGameplayTag, FShooterBufferedInput>`，删除覆盖循环与
  `RemoveAll` 谓词；处理时先 `MoveTemp` 再遍历，
  结构上保证「每个条目最多消费一次」。
- 保留 `GetInputBufferContext()` 上下文钩子与上下文校验
  （Weapon A 的按下沿不得在 B 上生效）。
- 保留 `IsOwnerPredictedFeedbackAllowedForContext` 的
  `UAbilitySystemComponent*` 参数并在头文件写明「刻意不读」：
  该测试用「这些复制状态存在也不参与 Owner 表现门控」做回归保护，
  删参数会一并删掉这组断言。
- `ShooterGameplayAbility_Reload.cpp` 中 `IsReloadTargetStillCurrent`
  的两处三目折行是工作区里已有的未提交版式改动，随本文件一并进入本提交。

## 遇到的问题

1. Emulated 第 1 次运行失败，服务器日志报：
   `Full-auto invariant verification invalid; OwnerFeedback=3 Authority=5
   Projectiles=5 AmmoConsumed=5 Cadence=true ExactlyOnce=true ActiveObserved=true`，
   同一行的 `Full-auto invariant report` 显示
   `ClientAmmo=35 ServerAmmo=34`。
2. 该阶段另一个客户端同一时刻的同类断言为
   `ClientAmmo=35 ServerAmmo=35 OwnerFeedback=4 Authority=4 ... Valid=true`。

## 处理方式

- 读断言实现确认失败条件是 `AmmoAfterRelease == BulletCountAfterRelease`
  （释放瞬间客户端镜像 Ammo 必须等于服务器权威 Ammo）；
  `OwnerFeedback` 与 `Authority` 只出现在报告文本里，
  且该断言明确允许相位差（只要求 `OwnerFeedbackDelta >= 2`
  与节拍不低于 `RefireRate`），本次 `minInterval=0.200 / RefireRate=0.200`
  也已满足。
- 因此失败点是 `PktLag=100` 下客户端 Ammo 镜像落后权威 1 发，
  与本次改动（输入语义、取消方式、生命周期清理）无关：
  同一断言在更早版本已有同样形态的失败记录，例如
  `Saved/Automation/Network/20260820_075825` 的
  `Full-auto release verification invalid; ClientAmmo=37 ServerAmmo=36`。
- 在同一份二进制上重跑 Emulated 阶段即通过（`20260918_120223`），
  两客户端全绿；该失败按既有不稳定断言记录，不在本轮修复范围。

## 遗留项

- GA_Equip 仍是 ServerOnly：迟到的复制 `State.Equipping` 仍可能吞掉一次按下
  （超窗即丢弃），彻底消除需要把装备事务也改为本地预测，本轮不做。
- 删除定时重试链后，「按住型重试在本地被拒」不再有 0.2s×2 的兜底，
  下一次机会只来自新的短暂阻塞解除事件；这是本轮明确接受的语义简化。
- 换弹相位差仍允许一次「本地窗口刚结束就开枪被服务器 Reject」的
  cosmetic phantom（不做 Ammo Prediction）。
- 网络阶段不覆盖「阻塞解除瞬间仍按住」的场景，HeldRepeat 只有自动化证据；
  若要网络级证据，需要给协调器新增一个「按住跨 blocker」阶段。
- 既有不稳定断言（`Remote invariant invalid`、`Full-auto release` 的
  客户端镜像 Ammo 相等、`Timed out waiting for network state`）不在本轮范围。
