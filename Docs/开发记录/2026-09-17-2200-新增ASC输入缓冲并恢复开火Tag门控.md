# 新增 ASC 输入缓冲并恢复开火 Tag 门控

- 日期：2026-09-17
- 计划提交说明：`GAS：新增输入缓冲并恢复开火Tag门控`
- 变更类型：生产代码 / 测试

## 目的

按 [输入缓冲与 Reload 本地预测执行计划](../执行计划/输入缓冲与Reload本地预测执行计划.md)
单元 1 实施：解决现有 Fire 路径「一次性 TryActivate 失败即永久丢输入」导致的客户端绕过硬门控问题。

改造前状态：

```text
按下 → AbilitySpecInputPressed → TryActivateAbility
→ 失败则这次输入永久消失
→ 为保住唯一一次输入，GA_Fire 客户端分支先于 Super::CanActivateAbility 返回，
  完全绕开 State.Reloading / State.Equipping / State.Dead 的 GAS Tag 互斥
```

改造后：

```text
按下 → TryActivateAbility
  ├─ 成功 / 硬失败（节拍未 Ready、武器无效等）→ 结束，不保留
  └─ 只被「短暂动作标签」阻塞 → 保留一次按下沿
       → 该标签解除后的安全时点重新尝试
       → 已被 Super 拦住的输入不再丢失，也不再需要绕过 Super
```

本提交不涉及 Ammo Prediction、Projectile Prediction、Reload 预测（属单元 2）。

## 本提交完成内容

### 生产：`UShooterAbilitySystemComponent` 输入缓冲

- 新增 `FShooterBufferedInput`（InputTag / Context / bHasContext / ExpireTime）与集中配置
  `InputBufferWindowSeconds`（0.15s）、`TransientInputBlockedTags`
  （`State.Reloading` / `State.Equipping`）、`FatalInputBlockedTags`（`State.Dead`）、
  `MaxHeldRetryPerPress`、`HeldRetryIntervalSeconds`。
- **失败分类只依赖引擎追加的具体阻塞标签**：订阅 `AbilityFailedCallbacks`，用
  `AppendMatchingTags(OwnedTags, FailureTags)` 求「本机 OwnedTags ∩ 失败标签」作为 BlockingTags。
  本项目没有配置 `GameplayAbilitiesDeveloperSettings`，通用失败标签是无效标签，因此不读取它们。
- 只有同时满足以下条件才保留按下沿：BlockingTags 非空、不与 Ability 自己的
  `ActivationOwnedTags` 相交（换弹中再按换弹这类重复按下直接丢弃）、全部落在
  `TransientInputBlockedTags` 内。
- **不保存第二份 held 状态**：是否仍按住直接读 `FGameplayAbilitySpec::InputPressed`。
- 安全时点：`RegisterGameplayTagEvent(TransientInputBlockedTags, NewOrRemoved)` 计数归零时只登记，
  合并到下一 Tick 的 `ProcessBufferedInputs()`，不在 Tag 回调栈内重入激活。
- 消费规则：消费前先移除条目（失败不重建、不延期）；按下沿在消费时已经松开则激活后立即走
  标准释放路径（`ServerSetInputReleased` + `AbilitySpecInputReleased`），不新增第二条结束 RPC。
- 按住型输入再武装：`IsSustainedInputAbility()` 且 `Spec.InputPressed` 且未激活时尝试启动，
  并允许 `MaxHeldRetryPerPress` 次间隔 `HeldRetryIntervalSeconds` 的有限重试（有上限，无死循环）。
- 生命周期清理：`InitAbilityActorInfo` / `ClearActorInfo` / `EndPlay` 清空意图并重建监听；
  `State.Dead` 出现时立即作废待消费意图；条目上下文变化（换枪提交、武器归还池）即丢弃。

### 生产：`UShooterGameplayAbility` 输入语义钩子

- 新增 `IsSustainedInputAbility()`（默认 false）与 `GetInputBufferContext()`（默认无上下文）
  两个最小声明钩子，以及 `IsBlockedByOwnActiveTags()`（读自身 `ActivationOwnedTags`，
  避免 ASC 访问引擎 protected 成员）。
- ASC 只消费这些声明，仍然不读 Weapon / Ammo / Inventory。

### 生产：`UShooterGameplayAbility_Fire` 门控收敛

- `CanActivateAbility` 客户端分支顺序改为：
  ASC/Avatar → 本机拥有者视图 → 当前武器有效且未隐藏 →
  **本地确定性条件（半自动节拍 Ready / 全自动仍按住）** → `Super::CanActivateAbility`。
  第 4 步先于第 5 步，保证节拍失败不产生 Tag 阻塞，因此永远不会被输入缓冲稍后补枪。
- 客户端不再绕过 GAS Tag 门控；弱网下迟到的阻塞标签只会把输入推迟到窗口内。
- 新增全自动「按住语义」门控（客户端与权威端都生效）：已经松开的按下沿不得启动连发，
  避免缓冲消费在主机本地视图上补出一次连发；远端请求的 `Spec.InputPressed` 由引擎按请求置位，
  因此不影响正常远端激活。
- 新增 `IsSustainedInputAbility()`（当前武器是否全自动）、`GetInputBufferContext()`（当前武器）、
  `IsInputHeld()`（读 Spec 输入状态）。
- 清理 `_Fire.cpp` 中已过期的「客户端必须先于 Super」注释，以及 `ShooterCharacter.cpp` 中
  `DoStartFiring` / `DoReload` / `DoSwitchWeaponInDirection` 三处「ServerOnly」注释漂移。

### 测试

- 新增 `Tests/Ability/ShooterInputBufferTestTypes.h`：4 个测试 Ability（按下沿、硬失败、
  自身标签阻塞、按住型），复用生产 ASC 输入路径与 GAS Tag 门控。
- 新增 `Tests/Ability/ShooterAbilityInputBufferAutomationTests.cpp`，9 个用例：
  短暂阻塞保留按下沿并按已松开状态补释放、按住时保持激活、硬失败不入缓冲、
  自身标签阻塞直接丢弃、过期不消费、上下文变化丢弃、按住型取消后再武装且次数有上限、
  按住后松开不再自动开始、死亡与 Avatar 生命周期清空意图。

## 遇到的问题

1. 首次编译失败：把 `InitAbilityActorInfo` / `ClearActorInfo` 覆写放在 `protected` 段，
   引擎把它们声明为 public，覆写降低可见性会让 `ShooterPlayerState` 与 `ShooterNPC`
   的既有调用点无法编译。
2. 测试夹具首次全部失败在「ASC 是否具备本机拥有者视图」：
   `FGameplayAbilityActorInfo::InitFromActor` 从 **OwnerActor 的所有者链**解析
   `PlayerController`，而 PlayerState 未由 PlayerController 拥有时解析不到。
3. `ContextChangeDropsPress` 用例用 `NewObject<UObject>` 造上下文对象时触发
   `UObjectGlobals.cpp:3447` 的 ensure（`UObject` 在 5.6 被标记为 abstract）。
4. **Dedicated 会话 `FireAfterReload` 阶段失败（重要，改变了对已批准语义的前提判断）**：
   GA_Reload 仍是 ServerOnly，其 `State.Reloading` 由引擎以
   `AddReplicatedLooseGameplayTags`（`GameplayAbility.cpp:974`）挂在拥有者 ASC 上，
   随 PlayerState 的复制节拍到达；实测服务器 GA_Reload 已结束 361ms，
   拥有者按 Fire 时该标签仍为 true。
   恢复 Tag 门控后这次按下被拦住并进入缓冲，150ms 窗口内标签未清除 → 该次点击被丢弃；
   旧代码绕过门控直接发请求（服务器已提交，所以能射出）。
   结论：「短暂阻塞会在窗口内解除」对**复制标签**不成立，短窗口无法覆盖该滞留。
   另一会话 `20260917_220306` 中同一阶段的标签已在按下前清除
   （`INPUT_BUFFER_TAG_CHANGED Tag=State.Reloading Count=0` 后按下，`ReloadingTag=false`），
   该阶段正常通过 —— 说明这是时序敏感，而不是恒定的逻辑错误。

## 处理方式

1. 把两个覆写移到 public 段，并加注释说明引擎的可见性约束。
2. 夹具改为用 `FActorSpawnParameters.Owner = PlayerController` 生成 `AShooterPlayerState`，
   并设置 `PlayerController->PlayerState`，与生产 `AController::InitPlayerState` 一致。
3. 用例改用两个已存在对象（PlayerState 与 ASC 本身）作为上下文，不再构造 `UObject`。
4. 就第 4 条与用户确认处理方式，结论为**保持已批准的短窗口与诚实门控不变，
   单元 2 直接接上**：GA_Reload 改为 LocalPredicted 后，拥有者的 `State.Reloading` 是自己的
   本地预测窗口（服务器的 `MinimalReplicationTags` 对 Owner `COND_SkipOwner`），
   该复制滞留从拥有者路径彻底消失，`FireAfterReload` 阶段随之恢复稳定。
   因此本提交只声明 Build / Automation 与不依赖换弹时序的网络证据，
   契约要求的缺失证据已在上方「验证结果」显式列出。

## 遗留项

- 单元 2（GA_Reload 本地预测）与单元 3（网络证据与收口）未实施。
- `State.Equipping` 仍是复制状态（GA_Equip 未预测），迟到时输入会被缓冲而不是丢弃，
  属行为改进，装备预测不在本轮范围。
- 输入缓冲只在「本机玩家自己的 ASC」生效；服务器上的远端 ASC 与 NPC 保持既有语义，
  因此 NPC 输入行为不变。
- 既有不稳定阶段（`Remote invariant invalid`、`Timed out waiting for network state`）未修复。
