# Inventory 类型头只依赖武器前置声明

- 日期：2026-10-07
- 计划提交说明：`重构：Inventory 类型头只依赖武器前置声明`
- 变更类型：生产代码

## 目的

`ShooterInventoryTypes.h` 是轻量数据头（FastArray Entry + 容器 + 少量查找
入口），却无条件 `#include "Weapons/ShooterWeapon.h"`，于是把该武器头的
6 个直接依赖（`GameFramework/Actor.h`、`Animation/AnimInstance.h`、
`Weapons/Animation/ShooterAnimNotify_WeaponSound.h`、
`Weapons/Interfaces/ShooterWeaponHolder.h`、
`Weapons/Data/ShooterWeaponConfigRow.h`、`Weapons/ShooterAmmoDisplayState.h`）
带给了包含它的全部文件；模块内共有 35 个文件（3 个头 + 32 个 .cpp）的包含
闭包里有这个头。

本提交只调整「谁需要看到完整 C++ 类型」：让轻量 Inventory 类型头只依赖
`AShooterWeapon` 的前置声明，把真正需要完整类型的实现移到 .cpp。
不改变 Inventory / Weapon 的任何 Gameplay 语义、数据结构与复制协议。

## 本提交完成内容

- `Source/ShootGame/Inventory/ShooterInventoryTypes.h`：
  移除 `#include "Weapons/ShooterWeapon.h"`，只保留 `class AShooterWeapon;`；
  7 个需要完整类型的实现由 inline 改为声明（`GetDebugString`、
  `AddItem`、`RemoveItem`、`FindItemByWeaponId`、`FindItem`、
  `FindAdjacentWeapon`、`PreReplicatedRemove`）。
- `Source/ShootGame/Inventory/ShooterInventoryTypes.cpp`（新）：
  集中承载上述实现，并在文件头写明「需要武器完整类型的实现集中于此」。
- 仍保留在头文件内的 inline：`NotifyWeaponEntryRemoved`（裸指针直传
  委托）、`NetDeltaSerialize`、`ClearItems`、`FindItemBySlot`、
  `PostReplicatedAdd` / `PostReplicatedChange`（空体）——它们不触碰
  武器类型，无需完整定义。
- 逐项按 A/B/C/D 分类判断后再动手：A（指针 / 参数 / `TObjectPtr` 成员）
  与 UHT 反射需求保留；B（成员访问、`TObjectPtr` 与裸指针的赋值 / 比较 /
  转换）全部移入 .cpp；本轮不存在 C（模板强制完整类型）与 D（sizeof /
  继承 / by-value）。
- 未新增任何抽象：没有 Manager / Interface / Component / Subsystem /
  friend / 反射字符串，只新增了一个最小实现文件。

## 遇到的问题

1. 不完整类型下的 `TObjectPtr` 赋值会落到
   `FObjectPtr::operator=(void* IncompleteOther)`，而该重载自 5.0 起已标记
   deprecated（`ObjectPtr.h:165-170`）；同理比较会经
   `IsObjectPtrEqualToRawPtrOfRelatedType`（`ObjectPtr.h:392`）比较
   `T*` 与 `U*`。因此这些实现不能靠「只留声明」蒙过去，必须移出。
2. 编辑过程中一次 `edit` 报 `ReplaceFileW EIO (Win32 1175)`（临时文件替换
   被占用）；随后用 `Measure-Object -Line` 读得 102 行（预期 127），
   一度疑似文件被截断。

## 处理方式

- 先读引擎源码确认 `TObjectPtr` / `FObjectPtr` 在不完整类型下的实际行为，
  再按 A/B/C/D 分类决定每一处是保留还是下移；A 类一律留在头文件，
  避免为了「零 include」破坏 UHT 或引入无谓的接口层。
- EIO 后重试成功；改用 `read` 工具与字节级检查复核（127 行、CRLF、
  UTF-8 无 BOM、无残留临时文件），确认 102 行是
  `Measure-Object -Line` 不计空行的读数假象，文件本身完好。
- 因最后一次改动仅为注释（说明 `PreReplicatedRemove` 为何下移），
  改完重编一次，使验证产物与最终源码一致。

## 遗留项

- `PreReplicatedRemove`（Owner Client FastArray 删除回调）与
  `GetDebugString` 没有 in-process Automation caller，真实复制到达路径
  只在联机会话中跑到；而普通 Dedicated 会话的死亡 / 重生尾段是既有已知
  失败（`Timed out waiting for network state; … damage=false death=false
  respawn=false matchState=false`，改动前最近 10 次会话均存在），
  故该回调本轮未取得运行时证据。现有证据为：函数体逐行原样搬移、
  链接通过、调用方（`InitializeComponent` 的委托绑定与 FastArray 模板
  实例化）未变。后续可加一条直接调用该回调的定向测试，或跑一次能走到
  服务器移除的会话补强。
- 审计提到的其它武器头依赖（Weapon → AnimInstance、
  Weapon → WeaponSound AnimNotify、Weapon → ConfigRow）本轮按范围要求
  未处理，属后续独立主题。
