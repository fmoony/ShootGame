# 收敛 HeldRepeat 的输入意图唯一来源为 Spec.InputPressed

- 日期：2026-09-18
- 计划提交说明：`重构：收敛 HeldRepeat 的输入意图唯一来源为 Spec.InputPressed`
- 变更类型：生产代码 / 测试 / 文档

## 目的

上一提交（`ea6728a`）把「按住可恢复」统一成 Spec 上的 `InputBehavior.HeldRepeat` 后，
FullAuto 的同一个输入意图仍同时存在于两处：

- 短暂阻塞期间的按下会登记一条 Buffered Press（`HandleAbilityFailed` 不区分语义）；
- 持续按住状态由 `Spec.InputPressed` 表达。

这条条目对 FullAuto 是死重：Release 后它仍留到过期，最终被消费时又被 GA_Fire 的按住门控拒绝
（`..._Fire.cpp:130-134`）。本提交冻结两种意图来源互斥，并删除这条冗余表达。

## 本提交完成内容

冻结语义（写入 ASC 头文件与标签注释）：

```text
无 HeldRepeat 的 Spec（Semi）    → pending intent 只由短期 Buffered Press Edge 表达
带 HeldRepeat 的 Spec（FullAuto）→ pending intent 只由 Spec.InputPressed 表达，Release 即终止
```

1. **登记侧**：`HandleAbilityFailed` 在失败分类通过后，若本次按下对应的 Spec 带 `HeldRepeat`，
   直接返回、不登记条目（不新增日志，保持日志减法）。
2. **消费侧硬化**：`ProcessBufferedInputs` 对带 `HeldRepeat` 的 Spec 丢弃历史残留条目
   （覆盖「按下时是 Semi、阻塞期间换成 FullAuto」的窗口），复用既有 marker
   `INPUT_BUFFER_DROPPED`、`Reason=HeldRepeat`，不新增 marker 名称。
3. **注释与文档**：ASC 头（职责 + 互斥语义）、`InputBehavior.HeldRepeat` 的声明与定义注释；
   计划文档 §4.1 / §5.3（分类第 5 条）/ §5.4（消费规则）/ §5.5 / §6.2 全自动时间线 /
   §13 验证矩阵第 4、5 条与新增 5b / §12 新增单元 5。
4. **测试**：
   - `InputBuffer.HeldRepeatRetriesAfterBlocker` 的断言由「held press is buffered」== 1
     改为「a held repeat press never registers a buffered entry」== 0，后续重试断言不变；
   - 新增 `InputBuffer.HeldRepeatDoesNotConsumeResidualEntry`：Semi 按下+松开留下条目后，
     在阻塞期间给 Spec 加上 `HeldRepeat`，断言残留条目不被消费、不产生本地动作边界
     （这是消费侧硬化的回归用例，去掉硬化即会失败）；
   - `InputBuffer.HeldRepeatReleasedPressIsNotRetried` 的注释按冻结语义更新，断言不变；
   - 测试文件头补上两种意图来源互斥的说明。

**不变**：Semi 的登记 / 绝对过期 / 上下文校验 / 只消费一次 / 消费后补标准 Release 全部不动；
Held 跨武器行为维持现状（不新增 `PressContext`）；无新增状态变量、无新增日志 marker、
无重试 Timer。

### 等价性依据（为什么删掉这条条目不改变结果）

对带 HeldRepeat 的 Spec，阻塞解除时今天的顺序是「先消费条目，再 Held 重试」，两者在同一个
`ProcessBufferedInputs()` 内、同一 Tick：

| 今天 | 本提交 | 可观测结果 |
|---|---|---|
| 条目消费 → 激活成功 | 无条目 → 重试激活 | 同样 1 次本地激活、1 次服务器请求、同样反馈 |
| 条目消费 → 本地拒绝 | 无条目 → 重试同一次尝试 | 同样被拒，仅少一次注定失败的尝试 |
| 条目因上下文变化 / 过期被丢弃 | 无条目 | 等同 |
| 已 Release → 条目消费 → 被 GA_Fire 按住门控拒绝 | 无条目、也不重试 | 等同（Release 即终止） |

关键依据：本地 `CanActivateAbility` 失败不会发出服务器请求——引擎
`InternalTryActivateAbility` 先做 `CanActivateAbility`
（`AbilitySystemComponent_Abilities.cpp:1796`），通过后才在 LocalPredicted 分支发
`CallServerTryActivateAbility`（`:1904-1933`）。因此少一次本地失败尝试不改变服务器
Reject 计数，也不改变 Ammo / Projectile / Shots 任何权威结果。

   Auth=3 Exact=false Stable=true`，同一阶段另一个客户端同类断言为

   但任何日志都没有失败标记；两个客户端都已跑完 `Reload-fire Case=2/1`
   （`Converged=true`）后会话结束。

## 处理方式

- `Remote invariant invalid` 的三元组（`Confirmed=2 / Montage=2 / Muzzle=2 / Sound=2 / Auth=3`）
  与本次改动前记录过的形态完全一致，历史出现于 `20260917_130103`、`20260917_150321`、
  `20260917_165744`、`20260917_191459`、`20260917_222726`、`20260917_223101`、
  `20260917_232558` 等会话，属于「远端观察窗口早于最后一发确认」的既有不稳定断言；
  本次改动只影响拥有者本地输入意图，不改变远端确认通道与服务器射速。
  在同一份二进制上重跑 Dedicated 即通过（`20260918_125554`，两侧 `Valid=true`）。
- Emulated 第 1 次是会话时长不足（60s 内在 `PktLag=100` 下跑不完全部相位），
  重跑把会话时长放宽到 90s 后通过；不是语义失败。
- 两处都按既有不稳定项记录，未修改测试与产品代码。
