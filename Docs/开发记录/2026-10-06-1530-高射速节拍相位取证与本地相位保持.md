# 高射速节拍相位取证与本地相位保持

- 日期：2026-10-06
- 计划提交说明：
  `修复：全自动本地开火节拍保持理论相位，并补齐节拍取证`
- 变更类型：修复 + 测试

## 目的

已知观测：600 RPM 达成约 9.997 / 10.000 shot/s（误差 0.03%），
900 RPM 达成约 14.485 / 15.000 shot/s（误差 3.43%），
低客户端 FPS 下 900 RPM 曾出现约 -8% 的射速损失。

本轮不改动 Server 权威射速规则（固定约 15ms 容差保持不变），
目标是先测清"这一枪为什么晚了"，再修改真正负责该延迟的地方。

## 只读审计：下一发目标时间由谁产生

`900 RPM 下，一发结束后，下一发理论目标时间到底由谁产生？`

调用链（全部为当前生产代码）：

```text
Held Fire（EnhancedInput Started → ShooterCharacter::DoStartFiring）
  → UShooterAbilitySystemComponent::AbilityInputTagPressed（只采集，不激活）
每帧一次：AShooterPlayerController::PostProcessInput
  → UShooterAbilitySystemComponent::ProcessAbilityInput
  → Held 分支：TryActivateInputTag → TryActivateAbility
  → GA_Fire::CanActivateAbility → CanLocallyStartFire
  → AShooterWeapon::IsLocalFireCooldownReady（Now >= LocalFireCooldownEndTime）
  → GA_Fire::ActivateAbility → 本地预测表现
  → AShooterWeapon::AdvanceLocalFireCooldown   ← 下一发目标时间的唯一产生点
  → GA_Fire::EndAbility（同步结束，不复制结束）
服务器：CanActivateAbility → CanAuthorityStartFire → CanCommitAuthorityShot
  → ActivateAbility → CommitSingleShot → TimeOfLastShot = Now
```

审计结论：

1. 下一发目标时间只由 `AShooterWeapon::AdvanceLocalFireCooldown` 产生，
   原实现是 `LocalFireCooldownEndTime = World->GetTimeSeconds() + RefireRate`，
   即 `CurrentTime + RefireRate` 形式——**存在**。
2. 本地侧没有任何 Timer，也没有"上一次目标时间 + RefireRate"的累加器；
   没有绝对目标时间，没有 Tick 之外的节拍来源。
3. `ProcessAbilityInput` 的 Held 分支每帧最多尝试一次激活，
   因此实际激活时间被量化到帧边界；`IsLocalFireCooldownReady` 用严格 `>=`。
4. `EndAbility` 与 `ActivateAbility` 在同一帧同一调用栈内完成，
   不存在"结束之后额外等一帧"的结构；逐发取证里
   `EndToActMs` 恒等于相邻两发的实际间隔，也从数据上否定了这一项。
5. 权威侧 `TimeOfLastShot` 写的是**服务器帧时间**，专用服务器实测约 29.89 FPS
   （33.46ms 一帧，由提交日志的帧号与世界时间差测得）。

## 取证设施

只加开发构建诊断，不改任何 Gameplay 结果：

- `ShooterWeapon`：按 PredictionKey 记录 `FShooterLocalFireCadenceSample`
  （`ExpectedDeadline` = 推进前的本地节拍终点、`Actual` = 本次激活时间、
  `LagMs`、`IntervalMs`、`FrameDeltaMs`、`EndToActMs`、`RefireRate`），
  并汇总 `FShooterLocalFireCadenceStats`（均值 / 最小 / 最大间隔、
  全窗口**累计相位误差** = 实际跨度 - 应然跨度）。
- 逐发日志：`FIRE_CADENCE_LOCAL`（拥有端）、`FIRE_CADENCE_SERVER_ACCEPT`、
  `FIRE_CADENCE_AUTHORITY_COMMIT`、`FIRE_CADENCE_REFIRE_REJECT`
  （服务器，含 `DeficitMs`）。
- 网络夹具新增矩阵模式 `-ShootGameFireCadenceMatrix`
  （复用 Ammo Prediction 夹具的全部驱动与观测，只替换步骤表）：
  5 个客户端帧率 × 2 个射速 = 10 行，每行按住 10 秒，
  客户端帧率由 `GEngine->SetMaxFPS` 下发并回读生效值。
- 矩阵只断言结构性不变量（接受数 == 权威发数、Pending 归零、记录归零），
  射速误差只作为数据上报。

## 判定结果：两条互相独立的真实原因

### 一、本地累计相位漂移（客户端侧，低帧率下为主因）

`LocalFireCooldownEndTime = Now + RefireRate` 以"本次实际激活时间"为重锚点，
每次被帧边界推迟的量都被永久写进后续每一发。

修复前实测（会话 `20261006_143945`，理论间隔 100.00 / 66.67ms）：

```text
组合            本地平均间隔   最小      最大      累计相位误差
30 FPS / 600    107.62 ms     100.000   133.36   +701 ms / 10s
30 FPS / 900     87.14 ms      66.668   100.02  +2334 ms / 10s
45 FPS / 600    111.13 ms     111.111   111.29   +991 ms / 10s
120 FPS / 900    71.11 ms      66.666    78.61   +622 ms / 10s
```

关键形态：最小间隔是"略小于理论周期的一帧整数倍"
（例如 60 FPS 下 6 帧 = 99.998ms < 100.000ms），
严格 `>=` 比较因此必须再等一帧，而这多等的一帧此后永不归还。
累计相位误差随发数单调增长，正是"迟到被永久累计"的形状。

### 二、权威侧间隔被服务器帧时间量化（拒绝的唯一来源）

所有 `FIRE_CADENCE_REFIRE_REJECT` 的 `SinceLastMs` 都塌缩到
**服务器帧时间的整数倍**（实测 33.46ms 一帧）：

```text
Step=103（45 FPS / 900 RPM）  5 次：33.4 33.4 33.4 33.4 33.5
Step=105（60 FPS / 900 RPM）  3 次：33.8 33.9 34.0
Step=108（120 FPS / 600 RPM）17 次：65.5 66.3 67.1 … 82.1（≈2 帧）
Step=109（120 FPS / 900 RPM）23 次：32.6 33.1 33.7 … 48.9（≈1 帧）
```

原因：`TimeOfLastShot` 写的是服务器帧时间，而请求包可以落在两帧之间的任意时刻。
若上一发的提交被记在帧 k、本发请求在帧 k+1 才被处理，
服务器量到的间隔就是 33.46ms——比真实请求间隔少整整一帧，
差额约 33ms 远超 15ms 容差，于是必然拒绝。
这也解释了为什么 900 RPM（间隔只比 66.67ms 大一点点）拒绝多，
而 600 RPM（100ms 有约 33ms 余量）拒绝少。

**这条不是客户端能修的**：本地请求节奏正确时，
服务器仍会因为自己的帧量化把"准时"看成"提前一帧"。

## 实施的修复（只改客户端本地节拍）

`AShooterWeapon::AdvanceLocalFireCooldown` 按模式分裂：

- 全自动：按**理论射速网格**推进（`上一次目标时间 + RefireRate`），
  落后达到一个完整节拍（掉帧 / 长卡顿 / 输入被阻塞一整拍）时重新基线到当前时间，
  绝不补发历史欠下的 Shot；并且不把下一发排到"本发实际时间 - 权威容差"之前，
  避免发出注定被拒绝的一帧追赶请求。
- 半自动：保持以本次真实击发为重锚点（语义未改）。
  半自动节拍是"每次击发后的冷却闸门"，没有持续射速目标；
  改成网格会让本地放行一次权威端必然拒绝的提前击发，表现为点击被吞掉。

同时把"未建立节拍"从 `-1` 改成哨兵时间 `NoLocalCadenceTime = -1000000.0f`，
使就绪判据不再需要特例分支（与 `TimeOfLastShot` 的既有写法一致）。

保证不会 burst：推进后的目标时间恒严格晚于当前时间；
重新基线也只产生一次新的节拍起点。

   `120 / 900` 为 33 / 24 / 14 / 25 次。它取决于"客户端帧网格相位"

4. 因此单看某一次运行，净变化是混合的：
   本地漂移最大的组合改善明显（`30 / 900` 从 -23.45% 到 -0.11%），
   而本地原本"偏慢但避开了拒绝"的组合仍可能出现两位数损失。
   原表现的稳定性来自"客户端慢下来换取服务器不拒绝"，不是可依赖的稳态。

## 夹具断言的分层修正

原射速用例用一条"达成射速 ±15%"同时覆盖两件事，
修复后必然失真：客户端请求节拍已经精确等于配置射速，
而权威达成率完全由权威门控的帧量化拒绝决定。

因此把断言拆成两层（`Rate600Rpm` / `Rate900Rpm`）：

1. **客户端请求节拍**（本仓库唯一能控制的量）：
   `ClientRequestRps` 必须在 ±15% 内——它正是上一版漏掉的回归：
   低帧率下按"实际时间 + RefireRate"重锚点会让请求节拍慢到 87 / 111ms，
   而权威达成射速因为"请求变慢、拒绝变少"看起来还行。
2. **权威侧结构性恒等式**：`Accepted == Shots`、
   `Accepted + Rejects == ClientActivations`（每一次请求要么被接受并提交恰好一发，
   要么被明确拒绝，没有中间态）、`Pending=0`、`Shot 记录=0`。
   权威达成射速本身只作为数据上报（`AMMO_PREDICTION_RATE_RESULT`）。

这项修正的直接触发证据：修复后的第一轮 `PktLag=100` 回归里
`Rate600Rpm` 出现 6 / 31 次权威拒绝、达成射速 8.057（-19.4%），
而结构性不变量全部成立（`Shots == Accepted`、`Pending=0`、`Records=0`）。

## 遇到的问题

1. 取证指标第一版在 `AbilityActivatedCallbacks` 回调里读 `TimeOfLastShot`
   作为"本发提交时刻"，结果每步第一发读到的是上一发的时刻，
   造出一个 1.77 秒的假间隔并把整行射速算成 0。
   根因是引擎顺序：`UGameplayAbility::CallActivateAbility` 先 `PreActivate`
   （其中 `NotifyAbilityActivated` 广播回调），再调用 `ActivateAbility`，
   所以回调**早于** `CommitSingleShot`。
2. 相位保持的第一版只做网格推进，30 FPS / 900 RPM 出现 33.335ms
   的"一帧追赶"间隔——那是必然被权威拒绝的请求，因此补上容差下界。
3. 半自动若一起改成网格，会在"迟到一次"之后放行一次
   早于 RefireRate 的点击（权威必然拒绝、点击被吞），故按模式分裂。
4. 单元测试首次运行失败：测试世界的 `GetTimeSeconds()` 接近 0，
   `LocalFireCooldownEndTime = Now - Lag` 变负并与 `-1` 哨兵冲突。
   改用 `NoLocalCadenceTime` 哨兵后语义清晰且测试通过。
5. `PktLag=100` 回归首次失败（`Rate600Rpm` 达成射速 -19.4%），
   见"夹具断言的分层修正"。

## 处理方式

1. 权威侧取证改用本帧世界时间；夹具注释写明该引擎顺序，避免再次踩坑。
2. 本地网格推进加"不早于本发实际时间 - 权威容差"的下界。
3. 全自动与半自动节拍语义分裂，各自有独立单元断言。
4. 哨兵时间统一为远早于世界时间的常量。
5. 射速断言按层拆分，并新增 `Accepted + Rejects == ClientActivations`。

## 遗留项与建议（本轮不实施）

1. **权威射速门控的测量基准需要设计决策**：
   `CanCommitAuthorityShot` 比较的是两个服务器帧时间，
   间隔被量化到 33.46ms 的整数倍，最坏把一次准时的请求看成提前一帧，
   超出 15ms 容差 → 必然拒绝；
   实测拒绝比例在 0%～24% 之间波动，且与客户端是否准时无关。
   建议方向是"按窗口 / 令牌桶判定平均射速"，
   而不是继续放大固定容差：放大容差会同时放宽真正的超射速边界，
   而令牌桶（净充速率 = RefireRate、容量约一帧）既能吸收帧量化，
   又不会允许持续超速。这需要先确认作弊边界再实施。
2. 矩阵只覆盖本机专用服务器 + 环回；`PktLag` 下的矩阵对照尚未跑，
   但拒绝机制来自服务器帧量化，与链路延迟无关（本轮 `PktLag` 回归里
   900 RPM 三次 0 / 1 / 0 次拒绝即为旁证）。
3. 900 RPM 在 30 FPS 下仍依赖"2 帧 = 66.67ms"这一临界对齐；
   若客户端帧率进一步下降（帧间隔 > RefireRate），
   本地节拍会按规则退化为"每帧最多一发"，这是有意的降级而非漂移。
4. `LocalFireCadenceSamples` 上限 1024 条，只限制取证内存。
