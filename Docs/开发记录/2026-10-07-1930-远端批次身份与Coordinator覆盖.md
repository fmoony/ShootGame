# 远端批次身份与 Coordinator 覆盖

- 日期：2026-10-07
- 计划提交说明：`修复：按批次身份重定义远端确认口径并补 Coordinator 覆盖`
- 变更类型：测试 / 文档

## 目的

普通 Dedicated 的远端确认阶段长期存在
`Remote invariant invalid: Confirmed=1 ... Auth=2 Exact=false` 假失败。

只读审查确认根因不在生产 Remote presentation：夹具把
"某个 baseline 到 Observer report 抵达服务器时为止的累计量"
当成权威增量，而 report 的到达时刻与 Observer 冻结时刻之间没有上界。
Target 完全可以在这段间隙里进入 SwitchCancel 再提交一发，
服务器随后现场读取权威计数就把这一发算进了上一批次。

因此本次提交只做两件事：

1. 在测试层把「被比较的权威 Shot」与「Observer 四路表现」绑定到
   同一个明确冻结的批次上（batch identity），不再依赖"双方碰巧观察了
   差不多同样长的时间"；
2. 为 `EvaluateRemoteConfirmedBatch` 的异步到达顺序与 exactly-once
   补上 Coordinator 层的最小自动化覆盖。

不修改任何生产 Gameplay、不新增生产 RPC 或生产状态。

### 批次两个边界的实现（测试 Coordinator）

- AuthorityStart：在 FullAuto 阶段 Arm 时冻结（复用既有
  `AuthorityShotsBeforeFullAuto`，未新造同义计数器），并固定统计武器；
- AuthorityEnd：在释放 + 静默期残留检查通过后冻结一次，之后
  SwitchCancel / Reload 等阶段的新 Shot 都不能改写；
- 开始边界：Target Arm 后同 tick 通知观察端 Coordinator
  （`NotifyObservedBatchArmed`），观察端据此建立四条基线并回 ack
  （`ServerReportRemoteBaselineReady`）；服务器只在 ack 到达后才置
  `bServerOwnBatchStartAllowed`，因此"基线早于批次第一发"是结构性成立；
- 收口边界：Target 收到拥有者释放上报时同 tick 发
  `NotifyObservedBatchFireEnded`，观察端在该信号第一次到达的 tick
  就地快照四路增量，不再等待、不用固定时间；
- 比较：`EvaluateRemoteConfirmedBatch()` 用
  「观察端快照」×「Target 自己冻结的批次边界」一次性比较，
  上报先到则推迟到冻结事件再比较，绝不在收到上报时现场读取权威计数。

## 遇到的问题

1. **基线锚点错位（镜像 race）**：观测端在"自己的 Arm"采样四路基线，
   而本机 Arm 可能早于对手**上一阶段（单发）**表现的到达。
   实测：本机 Arm `17.897`、本机基线 `17.930`、对手单发提交 `17.9298`
   → 基线落后 0.2ms，把上一发算进本批次（`Confirmed=Auth+1`）。
2. **收口边界过晚导致下一阶段污染**：把窗口收口放在"权威批次冻结"之后，
   而下一阶段（SwitchCancel）的开火许可与冻结同拍放行，
   下一发表现约 20~30ms 后到达观察端；一轮实测
   `SnapshotConfirmedDelta=3 / StableFor=0.000 / SettleRisk=true`
   正是该竞态。
3. **比较时点耦合**：观察端在 Target 打完瞬间就上报，权威终点还要等
   静默期验证，导致 report 先到时比较拿不到冻结值
   （`Cause=BatchNotFrozen`）。
4. **窗口开启被本机阶段门挡住**：窗口若以"本机释放上报"为门，
   本机释放晚于对手收口时，快照会包含对手下一发的表现。
5. **本地节拍断言与生产容差冲突**：开始边界要求等 ack，可能把全自动起手
   推迟约一个轮询拍；此后紧接的一发间隔合法下限是
   `RefireRate − AuthorityRefireTolerance`（0.015），
   而夹具原先写死 `RefireRate − 0.01`，比生产契约更紧。
6. 编译期：新增 TEST-ONLY 入口最初落在头文件 private 区（C2248）；
   测试直接读私有 `GetTestPlayerIdForTest`。
7. 版式门：新增日志的换行/参数布局、新文件 CRLF 与测试行长多轮不通过。

## 处理方式

- 基线锚点：改为由**被观测批次的 Arm** 驱动（服务器同 tick 通知观察端），
  该时刻一定晚于对手上一发表现的组播送达，又一定早于批次第一发。
- 收口边界：改由 **Target 射击动作结束**（收到拥有者释放上报）驱动，
  比批次最后一发的权威提交至少晚一个释放等待，
  又比下一阶段第一发至少早一个静默期；两端都靠结构顺序成立。
- 比较时点：`EvaluateRemoteConfirmedBatch()` 可被推迟——report 到达时若
  边界未冻结就只登记快照，冻结事件到达后再补做唯一一次比较；
  另加轮询兜底，保证直接通知丢失时不漏比较。
- 窗口开启：去掉"本机释放上报"这道门，窗口完全由被观测批次生命周期驱动。
- 节拍下界：夹具改用生产容差的测试镜像
  `AuthorityRefireToleranceSeconds = 0.015f` 作为下界，
  与生产契约对齐（该镜像保持现状，不新增 getter）。
- 编译与版式：把 TEST-ONLY 入口移入 public 区、去掉对私有身份访问器的
  依赖（身份由比较自身的交叉核对隐式验证）、修正 CRLF 与换行布局。

## 遗留项

- 普通 Dedicated 套件仍红，且都在本次目标之外：后段
  `Timed out waiting for network state; ... damage=false death=false
  respawn=false matchState=false`（death/respawn 段）。
- 45 秒会话窗口不足以让套件走到 `AUTOMATION_TEST_CLIENT_SUCCESS`。
- `AuthorityRefireToleranceSeconds = 0.015f` 是生产 protected 常量的测试
  镜像，留待 Server Rate Gate 专项统一处理（不新增 getter、不改可见性）。
- 回归中的 Ammo / WeaponContext / 节拍矩阵会话跑在本轮更早一轮二进制上
  （这些模式不经过远端批次路径）；如需最强证据可在下一次提交前重跑。
- AmmoPrediction PktLag=100 的 `Rate600Rpm` 仍是滞后敏感项
  （本轮恰好收敛，历史曾出现 15.99% / 19.43%）。
- 主观表现（枪声听感、后坐力手感、画面自然度）不由无头自动化宣告通过，
  仍需人工验收。
