# 换弹改为本地预测窗口并隔离服务器事务

- 日期：2026-09-17
- 计划提交说明：`GAS：改为本地预测换弹并隔离服务器事务`
- 变更类型：生产代码 / 测试

## 目的

按 [输入缓冲与 Reload 本地预测执行计划](../执行计划/输入缓冲与Reload本地预测执行计划.md)
单元 2 实施：GA_Reload 从 `ServerOnly` 改为 `LocalPredicted`，
让拥有者的换弹窗口与换弹表现在本地成立，同时把弹药转移与事务提交完整留在服务器。

直接触发原因（单元 1 实测）：`ServerOnly` 的 GA_Reload 其 `State.Reloading` 由引擎以
`AddReplicatedLooseGameplayTags` 挂在拥有者 ASC 上，随 PlayerState 的复制节拍到达，
服务器换弹结束 361ms 后拥有者仍持有该标签。恢复诚实 Tag 门控后，
这段滞留会让「换弹刚结束就按开火」的输入被本地拦下并在短窗口内过期。
改为本地预测后，拥有者的 `State.Reloading` 是自己的本地窗口
（服务器的 `MinimalReplicationTags` 对 Owner `COND_SkipOwner`），该滞留从拥有者路径消失。

## 本提交完成内容

### 生产：`UShooterGameplayAbility_Reload`

- `NetExecutionPolicy = LocalPredicted`；
  `bServerRespectsRemoteAbilityCancellation = false`（本地窗口到期绝不允许提前结束服务器事务）。
- `CanActivateAbility` 双端分流：
  - 预测端：ASC 与 Avatar 一致 → 本机拥有者视图 → 当前武器有效且未隐藏 →
    `Super::CanActivateAbility` 的 Tag 门控；
  - 权威端：`Super` + `ResolveReloadTarget` 完整真值校验
    （Inventory / Equipment / ownership / lifecycle / Magazine / Reserve / Dead）。
  - 客户端不再读取复制的 Magazine / Reserve：陈旧真值会把服务器本会接受的换弹请求挡在本地。
- 新增 `ResolveLocalReloadWeapon()`：预测端只取当前武器作为表现目标与本地时钟来源，
  不做任何弹药或 Inventory 判定。
- `ActivateAbility` 双端分流：权威端沿用原有事务路径；预测端只缓存武器、
  取消本地 GA_Fire 预测实例、按 `Weapon.ReloadDuration` 等待本地时钟。
- `HandleReloadWaitFinished`：预测端到期只结束本地实例
  （`bReplicateEndAbility = false`，不改 Ammo、不提交事务）；权威端提交路径不变
  （`bReloadCommitted` 单事务护栏保留）。
- 激活日志加入 `Side=Predicted` / `Side=Authority`，供网络场景区分两端实例。
- 新增测试观察接口 `ServerRespectsRemoteAbilityCancellation()`。

### 测试

- `ShootGame.Ability.Reload.ServerOnly` 改写为 `ShootGame.Ability.Reload.PredictedWindow`：
  断言 `LocalPredicted`、客户端不得结束服务器事务、InstancedPerActor、单事务、输入绑定与
  `State.Reloading` 归属。
- `ReloadEquip` 壳契约拆分为「GA_Reload 本地预测 / GA_Equip 仍 ServerOnly」，不再对两者用同一期望。
- 网络协调器 `Reload-fire` 阶段改为接受两条等价路径：
  要么请求已发出并被服务器 Reject（旧路径），要么在客户端本地就被拒绝、根本没有发出请求（新路径）；
  两条路径都必须满足无权威射击、无 Ammo 减少、无弹丸、无残留与本地表现上界 1。
- 网络协调器单发阶段（Owner accepted-shot evidence）加入前置条件：拥有者本地仍持有
  `State.Reloading` / `State.Equipping` / `State.Dead` 时不按下，等本地动作状态解除后再按，
  并记录等待时长。该阶段验证的是「一次被服务器接受的射击」的恰一次证据，
  阻塞期间按下的边界由 `Reload-fire` 阶段负责。

## 遇到的问题

1. `Reload-fire` 阶段在单元 2 首次运行时报 `PredictedDelta=0 ... Rejected=false Valid=false`：
   旧断言要求「客户端发出请求且服务器 Reject」，而本地预测后这次点击在客户端就被拒绝，
   服务器从未收到请求（无 Reject 计数），但同样没有产生任何权威结果。
2. 单发阶段在 Emulated 下首次运行时，一个客户端上报的 `Owner accepted-shot evidence` 全为 0
   （连本地 `FIRE_PREDICTED_OWNER` 都没有），失败信息为
   「did not satisfy immediate-feedback and exactly-once invariants」。
3. 三轮网络会话分别命中一次既有不稳定阶段：
   `Remote invariant invalid: Confirmed=2 ... Auth=3 Exact=false`（Dedicated，与本轮改动无关）
   与一次 Emulated 早期阶段失败。
4. 用 `powershell.exe -File` 传多元素 `-ServerExtraArgs` 数组时，数组被逗号拼成一个 token
   （`-ShootGameNetworkTest,-ShootGameSkipRemoteMontage,...`），协调器因此没有启用；
   必须像 `RunAll.ps1` 那样在本进程内用 hashtable 展开调用。

## 处理方式

1. 把该阶段的期望改写为「服务器 Reject **或** 客户端本地拒绝」两条等价路径，
   其余条件（无权威射击 / 无 Ammo 变化 / 无弹丸 / 无残留 / 上界 1 / 客户端收敛）一条不减，
   并在日志中分别输出 `ServerRejected` 与 `LocalRefused` 供归因。
2. 先补上「本地动作状态允许开火才按下」的前置条件；重跑 Emulated 后通过，
   判定该次失败为丢包下的阶段时序波动（当时该客户端在早期阶段没有任何本地开火活动），
   不是本次改动的确定性回归；下一次出现时按测试侧前置条件健壮性单独处理。
3. 既有不稳定阶段按既定约定不在本轮修复，重跑后通过。
4. 网络会话改用 `Saved/` 下的临时包装脚本在本进程内以 hashtable 展开调用（不进入版本库）。

## 遗留项

- 单元 3（网络证据收口、契约含义覆盖确认、路线规划更新）未完成。
- `GA_Equip` 仍为 ServerOnly：`State.Equipping` 仍是复制状态，仍可能迟到；

- 远端客户端看到的换弹状态仍来自服务器最小复制（只影响第三人称表现时机，不受本轮影响）。
- 既有不稳定阶段 `Remote invariant invalid` 与 `Timed out waiting for network state` 未修复。
