## 1. 5C 实施内容

### 1.1 GA_Equip ServerOnly 事务

`Source/ShootGame/AbilitySystem/Abilities/ShooterGameplayAbility_Equip.cpp/.h`：

- `CanActivateAbility` 保持与 GA_Fire / GA_Reload 相同的客户端预检顺序：
  - 非权威端只校验 `AbilitySystemComponent` 存在且 `GetAvatarActor() == AvatarActor`；
  - 该分支必须先于 `Super::CanActivateAbility`，避免读取可能过期的 `State.Equipping` / `State.Dead` 副本而吞掉单次输入；
  - 权威端执行完整校验。
- `ResolveEquipTarget`：按 Inventory Slot 顺序解析下一个合法实例，校验 Inventory 计数、目标 WeaponActor 归属、销毁中状态与“目标不能等于当前武器”。
- `ActivateAbility`：
  - 快照 `TargetInstanceId` / `PreviousInstanceId` / `CachedPreviousWeapon` / `CachedTargetWeapon`；
  - 用 `UShooterAbilitySystemComponent::CancelAbilitiesByTag` 显式取消 `Input.Fire` 与 `Input.Reload`；
  - 用 `UAbilityTask_WaitDelay` 等待 `TargetWeapon->GetEquipDuration()`；
  - 激活期间 GAS 自动挂 `State.Equipping`。
- `IsEquipTargetStillValid`：提交前二次校验目标实例仍存在、Active ID 仍等于快照、CurrentWeapon 未被其他路径改写、角色未死亡。
- `HandleEquipWaitFinished`：只提交一次；失败路径 `EndAbility(..., bReplicateEndAbility=true, bWasCancelled=true)`；`bEquipCommitted` 防重入。
- `CleanupEquipTransaction` / `EndAbility` 统一清理 Task 引用与事务成员，死亡、重生、断线不遗留 Equip 事务。

## 3. 规则依据与 UE 5.6 本地源码核对

与 GA_Reload / GA_Fire 同一规则，本提交的客户端预检顺序依据：

- Epic 官方文档：
  - `EGameplayAbilityNetExecutionPolicy`：`ServerOnly` 只在服务器执行，客户端仍允许发起激活；
  - `UAbilitySystemComponent::TryActivateAbility`：非权威端先调 `CanActivateAbility`，通过后才 `CallServerTryActivateAbility`；
  - Lyra Inventory and Equipment：拥有状态（Inventory）与当前装备世界表现（Equipment）分离，Ability 作为事务；
  - `UAbilityTask_WaitDelay`：用于服务器权威事务等待，不依赖 Montage。
- UE 5.6 本地源码已核对：
  - `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/AbilitySystemComponent_Abilities.cpp`：`TryActivateAbility` / `ServerTryActivateAbility_Implementation` / `InternalServerTryActivateAbility` / `InternalTryActivateAbility`；
  - `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/Abilities/GameplayAbility.cpp`：`CanActivateAbility` 中 `ActivationBlockedTags` 与 Owner Tags 的匹配逻辑。

结论：`ServerOnly` 的单次输入是否被转发，完全取决于客户端 `CanActivateAbility` 的返回值；客户端预检不得读取过期 Tag 副本。GA_Equip 沿用该规则。

## 5. 验证过程问题与处理

手动单独运行 Listen 会话时，最初只通过 `-ServerExtraArgs` 传 `-ShootGameSkipRemoteCurrentWeapon`，客户端未收到该跳过标志，导致客户端 `bRequireRemoteCurrentWeapon` 仍为 true，切换提交后停在远端 CurrentWeapon 一致性检查，出现“进程存活但无新日志”的假性挂起。

诊断方式：临时加入客户端 switch-wait / switch-report 诊断日志与 `OnRep_CurrentWeapon` 日志，确认 `Weapon` 已更新、`Active/Bound` 均有效、但 `Visible=false`。修复为按 `RunAll.ps1` 的正确配置同时传 `-ClientExtraArgs @('-ShootGameSkipRemoteCurrentWeapon')`。验证通过后已移除全部临时诊断日志并重新构建，最终回归不含诊断代码。

这不是产品缺陷，而是手动调用测试脚本时参数不完整。
