# Owner 表现与权威结果契约收敛

- 日期：2026-10-07
- 计划提交说明：`重构：分离 Owner 表现与权威结果，并修复普通网络夹具就绪门`
- 变更类型：生产代码 / 测试 / 文档

## 目的

本次提交把工作区里多轮累积的改动一次结清，主线是四件事：

1. **分离三层事实**：把 `Shot Intent`、`Owner Presentation`、
   `Authority Result` 正式拆开。服务器接受一发**不再**要求 Owner 事后补播一次
   瞬时第一视角表现，因此取消 Owner confirmed cosmetic backfill
   （`Backfill=1` 不再是 Accepted 的成功条件），并把四种 Owner 路径写进契约。
2. **Fire 的动作身份等于"玩家持有的武器"**：每把武器各拥有一份 `GA_Fire`
   Spec（`SourceObject = WeaponActor`），玩家与 NPC 共用同一语义，
   服务器无需新增字段即可复现武器身份。
3. **输入意图生命周期闭环**：Fire 的按住真值归输入采集层；Reload 补上
   `Completed` / `Canceled` 终点；Equip 这类单帧脉冲输入不再进入 Held。
4. **普通 Dedicated 夹具修复假失败**：先补齐身份取证，再补上 `OwnerSingleShot`
   缺失的就绪条件（"当前武器已拥有可解析的 Fire Spec"），消除"武器到了、
   Spec 还没到"却进入正向 single-shot 用例导致的全零报告。

## 遇到的问题

- 普通 Dedicated 反复出现全零 Owner 单发报告，但日志里没有玩家身份：
  两个客户端进程里"自己的" Actor 都叫
  `Coordinator_0 / Controller_C_0 / PlayerState_0 / Character_C_0`，
  无法区分是谁提交的报告。
- 取证结论显示：失败玩家 `PlayerId=257` 在按下时 `TagSpecs=0` /
  `SpecFound=false`（武器在、Spec 未到），同帧 Press+Release 因此没有形成任何
  动作边界，服务器 `Activated=0` / `Failed=0`，2 秒后按超时提交全零报告。
- Spec 被撤销时未结的本地预测记录没有明确清理边界；`RefundedCount` 曾把
  "预算退休"与"服务器拒绝"混在同一计数里；Spec Removal 生命周期退休曾被记成
  Server Reject。
- 编译期问题：`FGameplayAbilitySpec` 未在头文件前置声明，UHT 把返回类型解析成
  类成员；`Cast` 返回 const 指针赋给非 const 变量；新增自动化用例里一条断言
  方向写反（`TestFalse` 应为 `TestTrue`）。
- 版式门（redundant line break / one-param-per-line / 文档行宽 100）在新增日志、
  长表达式与开发记录上多轮不通过。

## 处理方式

- 身份取证：统一用服务器分配并复制的 `PlayerId` 作为跨端标识（`ClientIdx`
  只标注为"本端 PlayerArray 序号"，避免再次误归因），并给所有 Owner evidence
  报告补上身份与 Stage。
- 就绪门：`OwnerSingleShot` 在按下前要求
  `AShooterPlayerState::FindFireAbilitySpecForWeapon(CurrentWeapon)` 可解析
  （该判定与 `GA_Fire::DoesSpecMatchInputContext` 的 "SourceObject 就是当前武器"
  等价），未就绪则保持轮询等待；不新增固定等待、不重试、不改超时、不改判定。
- 预测债务：`Retired` 作为独立终结原因，只退预算并计入 Spec Removal 观测，
  不补播、不发 RPC、不计 Reject；`RefundedCount` 只统计真正执行了预算退还的记录。
- 编译与版式：补前置声明、修正 const 与断言方向；按版式门规则调整换行、
  参数布局与文档行宽。
- 契约冲突：以 `Docs/架构/网络射击AI自主验证契约.md` 为准更新四份历史执行计划的
  表述，保留历史证据但不把 `Backfill` 当作当前成功条件。
