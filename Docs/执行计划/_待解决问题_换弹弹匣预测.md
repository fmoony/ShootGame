- 源码基线：`9971ab1`；引擎：本机 UE 5.6.1。
- 定位：审计证据、结构性缺口、待验证假设与候选设计记录。
- 状态：未启动实现；Phase A～D 均为建议，不能据此视为已批准实施。

## 0. 证据分类与阅读边界

本文使用三种证据等级，候选方案单独标记，不与事实混用。

- **已确认事实 F**：直接从源码、引擎实现或蓝图读回验证的行为。
- **已确认结构性问题 S**：现有表达或生命周期本身存在缺口，可由结构推导。
  这不表示某一次现场故障已被该缺口唯一解释。
- **待复现风险 H**：代码路径允许某种异常，但没有针对性网络复现证据。
  不得描述为“已经发生”“已经定位”或“已确认 Bug”。

源码定位先经 CodeGraph，并以磁盘源码核对。
蓝图事实来自本对话前序审计在编辑器启动后的 MCP 只读读回。
本次仅整理文档并复核相关源码，没有重新执行蓝图审计或网络测试。
当前 `ABP_FP_Pistol` 的用户工作区改动不在本文的重新验收范围内。
Rifle TP 节点结论不自动推广为所有武器蓝图的逐节点结论。

用户报告过两种现象：第二次换弹本地有动画而远端无反应；远端换弹未收尾便出现射击。
这些是现场反馈，不等于已经取得对应 Owner / Server / Remote 的关联日志。
本文不能据此断言服务器提前开火，也不能断言第二次 Reload 已被服务器接受。

第 8 节提供文件、函数、蓝图图路径及外部资料索引。
后续应先形成可归因证据，再决定每一阶段是否实施及其具体数据结构。

## 1. 远端 Reload 表现

### 1.1 已确认事实：F-R1～F-R5

**F-R1：Reload Gameplay 由 GA_Reload 管理。**

`UShooterGameplayAbility_Reload` 使用 LocalPredicted 与 InstancedPerActor。
构造函数将 `State.Reloading` 加入 `ActivationOwnedTags`。
Owner 预测实例和服务器实例各自启动 `WaitDelay(ReloadDuration)`。
服务器在等待结束后复核目标，再调用 `ReloadFromReserve()` 提交弹药转移。
本地实例到期只结束本地窗口，不提交弹药转移；详见第 3 节。

**F-R2：AnimInstance 的 bool 是 ASC Tag 的本地读取结果。**

当前 PlayerState 创建并复制 ASC，采用 Mixed 复制模式。
编辑器配置读回确认 `ReplicateActivationOwnedTags=True`。
UE5.6 对 LocalPredicted 的 ActivationOwnedTags 使用最小 Tag 复制路径。
该路径 `MinimalReplicationTags` 的条件为 `COND_SkipOwner`。
Owner 使用本地 Ability 添加的 Tag；Remote 使用服务器复制到的 Tag。

`UShooterAnimInstanceBase::RefreshCommonAnimationData()` 每次更新查询 ASC。
它将 `HasMatchingGameplayTag(State.Reloading)` 赋给 `bIsReloading`。
`bIsReloading` 本身不是另一个复制字段，也不携带换弹序号或服务器时间。

**F-R3：Rifle TP 的 WeaponAction 状态条件已从蓝图读回。**

```text
ArmedAim → Reload：bIsReloading && !bReloadPresentationRecovering
Reload → ArmedAim：!bIsReloading || bReloadPresentationRecovering
```

EventGraph 的 `AnimNotify_ReloadRecovery` 调用 `BeginReloadPresentationRecovery()`。
该函数在 `bIsReloading=true` 时将 Recovery 标记设为 true。
`UpdateShooterAnimationData()` 在 `bIsReloading=false` 时将标记清为 false。
静态绑定清理路径也会清除它；正常连续换弹之间主要依赖前述 false 观测。

**F-R4：当前 Reload 状态的 `bAlwaysResetOnEntry=False`。**

这是状态节点实际读回值，不代表已经证实某次混合重入使用了错误播放位置。

**F-R5：当前远端没有服务器时间相位补偿。**

Rifle Reload 的 Sequence Player 使用 `MM_Rifle_Reload`。
节点为 `StartPosition=0`、`PlayRate=1`、`bLoopAnimation=False`。
没有绑定服务器开始时间、持续时间或网络动画进度。
正常初始化进入时从头播放，起点随该端收到状态并评估转换的时机确定。
快速重入是否重置还受状态混合与 F-R4 影响，不能保证每次重入都从零开始。

### 1.2 已确认结构性问题：S-R1～S-R3

**S-R1：单个 bool 只能表达“正在换弹”，不能表达“新的一次换弹”。**

假设两次动作之间的 false 未被观察端读取，远端只看到持续的 true。
即使底层 Tag 容器又复制了一次，读取相同 bool 也不能识别新的动作身份。

```text
Server：Reload 1 true → false → Fire → Reload 2 true
Remote：观察到 true ─────────────────→ 观察到 true
```

该示意证明表达缺口，不是某次网络会话的实测时间线。

**S-R2：Recovery 的清理依赖观察到 false，存在跨动作残留条件。**

在 S-R1 条件成立且没有其他清理路径时，旧 Recovery=true 会阻止再次进入 Reload。
结构上的条件链已确认；现场是否真正发生这一链条属于 H-R1。

**S-R3：仅开启 Always Reset on Entry 无法补足动作身份。**

该选项处理重新进入状态时的初始化；不能强制产生遗漏的退出、进入或动作边界。
Recovery 已经挡住进入时，改变重入复位选项也不能替代新动作识别。

### 1.3 待复现风险：H-R1、H-R2

- **H-R1**：用户报告的第二次 Reload 无反应，可能来自服务器拒绝，也可能来自远端漏播。
  尚未用同一次请求的关联日志区分这两条路径。
- **H-R2**：快速重入时残留混合权重与不强制复位可能影响播放位置。
  目前只有节点配置证据，没有针对性 PIE 复现。

### 1.4 候选方向：不是最终方案

阶段 1 可评估 `ReloadId` / `ReloadSequence`。
服务器每次正式接受一轮 Reload 时递增，Remote 收到新 ID 后初始化新一轮表现。
初始化应考虑旧 Recovery、旧动画和旧 Magazine 表现的清理。
开始、结束或取消边界可考虑主动请求复制更新。
ID 的宿主、位宽、生命周期、回池重用和结束状态表达尚未决定。
序号可识别最新动作，不保证补播所有已经结束的历史动作。

阶段 2 仅在实测仍存在明显相位问题时评估 `ServerStartTime + Duration`。
Remote 可依据 GameState 的服务器时间估计恢复动画进度。
必须同时处理跨过 Detach / Insert 后的弹匣状态恢复，见第 5 节。

## 2. 跨 Actor 表现时序

### 2.1 已确认事实：F-T1、F-T2

**F-T1：换弹、开火与武器表现来自不同通道。**

- Reload Tag：PlayerState 上的 ASC，经服务器复制到 Remote。
- Character 动画状态：AnimInstance 查询本机 ASC，再由 TP AnimBP 评估。
- 开火 Montage：服务器调用 Character 的 `MulticastPlayFiringMontage()`。
- 枪口与音效：服务器调用 Weapon 的 `MulticastPlayFiringFX()`。
- Projectile：服务器 `Fire()` 路径生成 Actor，其实例通过复制到客户端。

两处开火 Multicast 当前均为 Unreliable。
Remote 开火表现来源是服务器确认；不应称为“Owner 预测被直接广播到远端”。
当前 Reload 动画、Fire 表现和 Weapon 表现没有统一动作身份与时间轴。

**F-T2：正式 PlayerState 的源码配置继承引擎默认低更新频率。**

GameMode 蓝图的 `PlayerStateClass` 读回为原生 `AShooterPlayerState`。
UE5.6 的 `APlayerState` 构造函数设置 `NetUpdateFrequency=1`。
项目源码未为该类覆盖这一频率，也未在 Reload 起止路径主动刷新 ASC 宿主。
武器扣弹和换弹提交会调用 Weapon 自身的 `ForceNetUpdate()`。
这不会等价刷新 PlayerState 上的 Tag。

上述结论是配置与调用链事实，不是实测每次复制间隔恰好一秒。
实际到达时机仍受网络调度、其他更新请求、帧率、丢包和相关性影响。

### 2.2 结构性问题 S-T1 与假设 H-T1

**S-T1：跨 Actor 数据没有共同表现顺序，无法用某一通道到达推断其他通道已就绪。**

服务器结束换弹后合法开火，Remote 仍可能尚未更新换弹状态或完成动画收尾。
这是现有同步表达的缺口，不是服务器违反 Gameplay 门控的证据。

**H-T1：低更新频率可能放大现场相位差，尚未证明它是唯一原因。**

需要对照服务器事务结束、Remote Tag 到达、动画进度与射击事件到达时间。
不能只根据 Remote 画面判断服务器是否在换弹期间开火。

### 2.3 三类候选改进的职责不同

- `NetUpdateFrequency` / `ForceNetUpdate`：改善更新及时性，不保证每个中间状态被观察。
- ReloadId：区分动作身份，解决“又换了一次”的表达问题。
- 服务器时间信息：用于表现相位恢复，不决定换弹事务是否成功。

提高频率不能替代 ID；ID 也不能单独补偿动画相位。
跨 Actor 的顺序保证需遵循 UE 的实际规则，不能依赖当前无丢包时的偶然顺序。

## 3. Ammo Prediction

### 3.1 已确认事实：F-A1，服务器权威边界

- `ConsumeAmmo()` 要求 HasAuthority、有效消费量和足够弹药。
- `ReloadFromReserve()` 要求 HasAuthority，按缺弹量和备弹量决定真实转移。
- `Fire()` 在客户端直接返回；服务器消费成功后才执行弹丸生成与表现。
- GA_Reload 本地到期调用 EndAbility，`bReplicateEndAbility=false`。
- Fire / Reload 均设置 `bServerRespectsRemoteAbilityCancellation=false`。
- Fire 服务器激活先执行 GAS Tag 门控，再检查武器、弹药及节拍等条件。
- Reload 服务器激活检查 Tag、装备归属、背包、生命周期和弹药转移资格。
  提交时再次检查目标有效性，再由 Weapon 提交弹药。

所审正常路径中，客户端没有直接提交权威弹药或提前结束服务器换弹事务。
这是静态调用链结论，不等价于已经完成全部网络互斥、重复提交和取消场景验证。

### 3.2 已确认事实：F-A2，当前预算与确认方式

`PendingPredictedShots` 是非复制的本地待确认消费计数。
只有非权威端的本机玩家视图维护该预算，Listen Host 不使用此 Pending 机制。

```text
GetPredictedMagazineAmmo() = max(0, MagazineAmmo - PendingPredictedShots)
```

本地有效消费增加 Pending，不写复制的 MagazineAmmo / ReserveAmmo。
`OnRep_MagazineAmmo(OldMagazineAmmo)` 目前按数值差处理：

- 新值下降：按下降量减少 Pending，最小为 0。
- 新值上升：认为建立新基线，将 Pending 清零。
- 数值相同：没有可用于区分补弹与射击事件的差值。

`GA_Fire::EndAbility()` 在 Rejected 且 CachedWeapon 有效时退还本次预测消费。
该函数随后清空 CachedWeapon；下一次激活会重置本次预测发数。
TryOwnerPredictedShot 的预算检查只控制本地表现和节拍，不阻止 Ability 请求服务器。
预算不足不结束 FullAuto Ability，也不停止其预测 Timer。

### 3.3 代码层风险，待复现：H-A1～H-A3

**H-A1：仅根据 MagazineAmmo 差值，可能错误确认或遗留预测消费。**

```text
最后快照 29 → 服务器 Reload 到 30 → 服务器 Fire 到 29
下一份可见快照仍为 29
```

中间事件可能被合并，最终数值不能单独表达补弹和消费发生过。
上升快照到达时，也可能存在补弹后新产生、尚未确认的本地消费。
当前统一清零是否误清这些消费，需要网络复现与请求归因验证。
信息表达不足可由结构推导；具体 Pending 错误或 HUD 异常仍为待复现风险。

**H-A2：迟到 Reject 存在无法对应原预测消费的风险。**

玩家先松开或被取消，可能已清空 CachedWeapon；新激活还可能复用同一 Ability 实例。
旧请求 Reject 到达时，现有退款路径可能缺少原消费的武器或激活上下文。
本机引擎按 PredictionKey 匹配实例，故不能假定旧拒绝一定进入当前实例的退款分支。
尚未取得“原消费发生、对应拒绝到达、退款未发生”的完整网络证据。

**H-A3：服务器已允许开枪，本地预算仍基于旧快照，可能缺少 Owner 预测表现。**

例如空弹 Reload 的本地窗口结束后立即 Fire，本地复制值可能仍为 0。
预算可以拒绝本地表现，但 Ability 请求仍可能被已经完成补弹的服务器接受。
这可能形成服务器开枪而 Owner 没有对应首枪预测表现的窗口。
该路径为代码层风险，待针对性复现；不是已证实的现场故障。

### 3.4 候选改进方向：不决定数据结构

- 为预测消费增加可确认身份，并明确其与武器生命周期的关系。
- 评估 Activation Identity + Shot Sequence / Processed Shot Count。
- 确认、拒绝和新弹药基线应有可归因语义，而非只看数值升降。
- Prediction bookkeeping 应能活过 GA_Fire 的本地结束，直到结果可结清。
- FullAuto 双端独立计时，需明确本地预测发数与服务器实际发数怎样关联。
  一次 GAS PredictionKey 激活确认不能等同于整段 FullAuto 每发都确认。

不在本文决定 Ledger、字段布局、RPC、复制快照或 Ammo Attribute 的最终选择。
GAS 的 caught-up 回调也不能未经验证就充当另一个 Actor 弹药快照的到达证明。

## 4. HUD

### 4.1 已确认事实 F-H1 与结构性缺口 S-H1

`GetPredictedMagazineAmmo()` 已存在，但当前 HUD 尚未统一消费预测结果。
`PushAmmoToOwnerHud()` 仍传 MagazineAmmo、MagazineSize、ReserveAmmo 权威快照。
TryConsumePredictedAmmo 和 RefundPredictedAmmo 没有形成统一 HUD 变更通知。

当前仍有多处读取入口：

- Weapon：PushAmmoToOwnerHud。
- Character：OnWeaponActivated、EnsureCurrentWeaponPresentation。
- Controller：绑定或刷新 HUD 时读取当前 Weapon 的 GetBulletCount。
- Character 的 UpdateWeaponHUD 广播后，Controller 转交 BulletCounterUI。

S-H1：预测预算和 HUD 数据流尚未闭合，后续补一个 Getter 无法覆盖全部刷新来源。

### 4.2 候选方向与前置条件

HUD 应在 Prediction Convergence 机制稳定后再统一。
可评估 DisplayAmmo / LocalDisplayedAmmo 作为统一显示数据入口，覆盖：

- predicted fire；
- authoritative confirm；
- reject refund；
- reload；
- weapon switch；
- respawn / pool reuse。

这些名称只是候选语义，不表示已经决定新增成员或第二份完整弹药镜像。
不要现在直接把所有 GetBulletCount 替换成 GetPredictedMagazineAmmo。
换弹本地结束时是否预测显示补满，需要另行明确转移预测及失败纠正体验。
本地显示变化不等于服务器 Magazine / Reserve 已经转移。

## 5. 与 Magazine Presentation 的关系

### 5.1 已确认事实：F-M1

此前已验收的 Rifle 第一人称姿势链路保持为：

```text
TP Reload → TP Character Mesh → FP Copy Pose → FP 程序化表现
```

Magazine Notify 接受 TP Character Mesh 为时间来源，不要求 FP 再触发一次 Notify。
`UShooterAnimNotify_WeaponMagazine::Notify()` 拒绝 Dedicated Server 表现执行。
它检查角色、TP Mesh、bIsReloading、CurrentWeapon 及武器 Owner。
当前代码对本机人类玩家执行 FP 分支，并继续执行 TP 分支；Remote 只执行 TP 分支。
因此不能把早期“Local 只处理 FP”的设计意向直接写成当前 Notify 的全部实际行为。

Detach / Insert 只操作 Proxy、挂接、骨骼可见性与局部 Transform。
它们不写 Ammo，不决定 Reload 成功，不承担 Ammo Commit。
ResetMagazinePresentation 是表现恢复入口，不能代替服务器事务清理。

### 5.2 时间校正的条件性风险：H-M1

若未来引入 Remote Reload 时间跳转，需要处理以下状态恢复：

- 已跨过 Detach、尚未到 Insert：恢复该阶段应有的手持 Proxy 与原弹匣隐藏状态。
- 已跨过 Insert：恢复枪上原弹匣，隐藏并复位 Proxy。
- Notify 因跳转未触发：依据对应 Reload Phase 恢复目标状态。
- 回拨或重复校正：避免重复 Detach / Insert 和旧动作覆盖新动作。
- 已取消、切枪或动作身份变化：旧阶段不能重新影响当前武器。

目前没有加入上述时间校正，也没有证实当前已经发生“跳转漏 Notify”。
这里只记录未来方案的约束，不能依赖 Notify 恰好逐帧经过。
Phase 的来源、如何读取动画阶段及恢复接口，均留待 Phase B 评估。

## 6. 建议实施顺序，非已决定方案

本节提供后续拆分依据，不是立即执行的工作单。
不要一次实现全部阶段；每阶段应先审查前置证据和影响范围。

### Phase A：动作身份与复制及时性

先增加针对性诊断和网络复现，区分服务器拒绝与 Remote 漏播。
再评估 ReloadId、关键边界主动复制更新和合理的宿主更新频率。
重点验证连续 Reload 与 Reload → Fire → Reload。
不能以调高频率后的偶然正常，证明动作身份缺口已经解决。

### Phase B：条件性的远端相位补偿

仅在 Phase A 后仍实测到明显相位落后时，评估 ServerStartTime + Duration。
同时评估时间跳转、动画收尾及 Magazine Phase 恢复。
未经测量，不将新增时间同步字段定为必做项。

### Phase C：Ammo Prediction 归因与收敛

先为 H-A1～H-A3 建立针对性复现测试。
根据实际失败场景决定是否引入 Activation / Shot acknowledgement。
需区分半自动单次激活和 FullAuto 连续发数，不预定统一数据结构。

### Phase D：统一 HUD

预测确认与纠错稳定后，统一显示入口和刷新通知。
再明确是否包含本地预测换弹后的补弹显示。

所有阶段都应保持五条网络不变量：Owner 即时反馈、本地规则与收敛、服务器最终权威、
Remote 仅确认表现、一次认可动作恰好一份权威结果。
上述断句只列不变量主题；完整含义以项目验证契约为准。
后续正式实施方案需逐条填写影响维度、保持维度、新增证据和排除范围及理由。

## 7. 后续验证清单

### 7.1 每个场景都必须分别观察三端

- Owner：输入、预测激活身份、窗口、表现、预算、HUD、收到的确认或拒绝。
- Server：请求身份、接受或拒绝及原因、Tag、事务起止、Ammo 转移与真实发数。
- Remote：武器与角色身份、Tag 到达、换弹动作识别、动画进度、Recovery 与 Proxy 状态。

服务器未接受时 Remote 不播放换弹，不能直接判定为远端复制失败。
不同进程日志时间不能直接相减，必须标明时钟域并关联同一动作。
日志字段需考虑网络模式、角色、武器生命周期和激活身份；当前不假定已有 ReloadId。
以下场景全部待执行，不得用已有其他场景的绿色报告代替。

### 7.2 场景及判定重点

1. **连续快速 Reload**：三端区分重复输入、被拒请求与新接受动作。
   不要求正在换弹时再次按键一定建立新事务。
2. **Reload → 开一枪 → 立即再次 Reload**：关联两次服务器事务及中间真实扣弹。
   对照 Owner 第二次预测与 Remote 第二次动作是否属于同一接受请求。
3. **Remote 是否漏掉第二次 Reload**：检查 false 是否被观察、Recovery 是否清理。
   同时检查服务器到底接受还是拒绝，不能只统计远端动画次数。
4. **Remote 动画是否明显晚于服务器事务**：记录状态送达和动画进度。
   区分传输延迟、复制调度、从头播放与退出混合造成的差异。
5. **空弹 Reload 完成后立即 Fire**：同时看本地预算、预测表现和服务器首枪。
   检查是否出现权威开枪但 Owner 未预测表现的窗口。
6. **快速点击 Fire + 迟到 Reject**：先证明消费和对应拒绝确实发生。
   再验证本地实例结束或重新激活后，原消费能否准确退款。
7. **FullAuto 跨权威弹药快照**：比较预测发数、实际发数、Pending 和生命周期。
   包含多个消费合并、补弹与消费抵消、上升快照晚到及停止后结算。
8. **Reload 期间 Cancel / Weapon Switch / Death**：检查三端旧动作是否收敛。
   分别观察服务器有无错误提交、Owner 清理、Remote 动画与 Proxy 是否恢复。
9. **远端时间校正后的 Detach / Insert**：仅在相关方案实现后执行。
   覆盖跨 Detach、跨 Insert、重复校正及旧动作消息迟到。

优先覆盖 Dedicated 的 Owner / Server / Remote 三端，再按变更补充 Listen Host 去重。
涉及延迟、抖动和丢包的假设需采用相应网络条件，不能只测零延迟 PIE。
每次检查 Authority Ammo、提交次数及 Projectile 增量，不以动画视觉替代事务证据。
