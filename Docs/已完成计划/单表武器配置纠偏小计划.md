# 单表武器配置纠偏小计划

## 1. 目的

将当前武器配置从：

```text
DT_WeaponData 行
→ WD_* WeaponDefinition 资产
→ BP_ShooterWeapon_* 默认值
```

收敛为：

```text
DT_WeaponData（唯一武器模板库）
→ Pickup 蓝图/关卡实例只选择一行
→ 该行决定 WeaponActorClass、玩法参数与表现资源
```

本计划是 [武器与 Inventory 正式架构实施计划](武器与Inventory正式架构实施计划.md) 的纠偏插入项。当前 Actor Pool 与 WeaponActor 生命周期成果保留；在继续 B3 以前，先完成本计划，撤销不符合项目规模的 `WeaponDefinition + PrimaryAssetId` 配置层。

本文只规划，不授权立即修改源码或资产。

## 2. 最简结论

- `/Game/Shooter/Data/DT_WeaponData` 是唯一武器模板数据源；一行描述一类完整武器。
- RowName（`Rifle / Pistol / AWP / GrenadeLauncher`）就是配置键，不再另设 `WeaponId` 或 `DefinitionId` 字段。
- Pickup 保留一个 `FDataTableRowHandle`；设计者在蓝图或关卡实例中选择行，不写 Switch，也不再选择 `WD_*`。
- 表行保留 `WeaponActorClass`，用于选择对应武器蓝图实现；蓝图只承载确有必要的结构或逻辑差异，不再承载可表格化数值。
- Inventory 复制 `WeaponRowName` 和实例状态，不复制整行配置。
- 保留 `InstanceId`：它只是区分“背包中的这一把”的运行时句柄，用于弹药、装备事务、Actor 池绑定和移除；它不是策划配置 ID，也不需要人工填写。
- Pickup 自身不增加唯一 ID。场景中的 Actor 已有网络身份，武器类型由所选 RowName 表达。

## 3. 当前事实与纠偏原因

只读审计确认：

- 当前 `FWeaponTableRow` 只有预览网格和 `WeaponDefinition` 软引用；DataTable 实际只是索引。
- `WD_Rifle / WD_Pistol / WD_AWP / WD_GrenadeLauncher` 再保存 ActorClass、Ammo、Fire、Presentation 和 FireBehavior。
- 大量真正生效的属性仍留在 `BP_ShooterWeapon_*` CDO；Definition 中部分 Fire/Presentation 字段目前还未进入生产消费路径。
- 四个武器蓝图没有足以支撑三层配置的自定义图逻辑，现状形成了“表、Definition、蓝图 CDO”三份来源。
- `FShooterWeaponInstanceData::InstanceId` 已参与 Inventory、Equipment、异步装备和池化 Actor 的关联，不能与多余的配置身份一并删除。
- Definition 的 `FiringRecoil` 元数据限制非负，但现有武器值包含负数；迁移时必须统一语义和约束，不能机械复制。

因此，本项目目前不需要 AssetManager 驱动的武器定义资产体系。它增加了资产数量、迁移工具和解析路径，却没有带来本阶段需要的分包、按类型扫描或独立资产生命周期收益。

## 4. 目标数据结构

将 `FWeaponTableRow` 扩展并更名为完整的 `FShooterWeaponConfigRow : FTableRowBase`。首版只纳入已经存在且会被生产逻辑消费的字段：

| 分组 | 字段范围 |
|---|---|
| Actor | `WeaponActorClass` |
| Ammo | `MagazineSize`、`InitialReserveAmmo` |
| Fire | `bFullAuto`、`RefireRate`、`AimVariance`、射击噪声参数 |
| Timing | `ReloadDuration`、`EquipDuration` |
| Attack | `FireBehaviorClass`、`ProjectileClass`、`MuzzleOffset` |
| Socket | `MuzzleSocketName`、`LeftHandGripSocketName` |
| Mesh / Anim | 第一、第三人称 Mesh，Pickup Mesh，第一、第三人称 AnimClass，FiringMontage |
| FX / Audio | MuzzleFlash、FireSound、三段换弹音效 |
| View | `FiringRecoil`、`FirstPersonCompositionDrop` |

约束：

- 不为了表格观感新增没有消费者的字段。
- 不把当前弹匣、备弹、装备状态、计时器或 Actor 指针放入表中。
- `FireBehaviorClass` 只选择无持久可变状态的行为类；投射物等每种武器参数仍保存在同一行。
- 资源引用首轮沿用当前同步加载边界，不在本纠偏中同时引入异步流送框架。
- 由一个集中解析入口负责 `RowName → ConfigRow`，不恢复第二套 Registry 或 Primary Asset 映射。

## 5. 运行时数据流

### 5.1 Pickup

```text
BP_ShooterPickup（或关卡实例）选择 WeaponType 行
→ OnConstruction 读取 Pickup Mesh
→ Authority Overlap 校验同一行
→ Inventory.TryAddWeaponRow(RowName)
```

`RespawnTime` 留在 Pickup 上，因为它描述刷点/关卡节奏，不是武器模板属性。用户已修复的重生逻辑门只做回归验证，不重写。

### 5.2 Inventory

`FShooterWeaponInstanceData` 收敛为：

```text
InstanceId       // 服务器生成，纯运行时
WeaponRowName    // 武器模板行名
MagazineAmmo
ReserveAmmo
SlotIndex
```

重复武器类型判定由 `DefinitionId` 改为 `WeaponRowName`，保持现有“一名玩家不能重复持有同一武器类型”的行为。若未来允许同型号双持，只调整重复策略，不改表结构。

### 5.3 WeaponActor

- Actor 获取并复制 `WeaponRowName`，客户端与服务器通过同一张表恢复只读配置。
- Acquire/Bind 时应用行数据；Release 时只清运行时状态，不修改模板数据。
- FireBehavior 读取当前行提供的上下文，不再解析 Definition 资产。
- `WeaponActorClass` 仍由表行决定，因此当前武器蓝图可先保留；完成迁移后再判断是否都能指向一个通用 Weapon 蓝图。

## 6. 实施顺序

### C0：冻结基线并建立迁移清单

- 暂停继续扩大 DefinitionId 在 B3/B4 中的使用。
- 导出四个正式武器在 DataTable、`WD_*` 和蓝图 CDO 中的现值，逐字段确定最终值。
- 明确 `FiringRecoil` 的正负语义并修正字段约束。
- 增加“所有正式行完整且可解析”的数据测试。

验证：只运行配置完整性测试和现有 Definition/Inventory 相关定向测试；不跑完整回归。

### C1：建立完整表行并迁移资产值

- 新建完整行结构，将四种武器的最终值写入 `DT_WeaponData`。
- 表行直接引用对应 `WeaponActorClass` 和 FireBehavior 类。
- Pickup 蓝图只保留 RowHandle 选择；不再引用 `WD_*`。
- 通过 Unreal Editor 资产系统修改并保存 DataTable/Blueprint，禁止直接写 `.uasset`。

验证：逐行校验配置与软引用；四类 Pickup 的预览和行选择正确。只做定向测试。

### C2：切换生产消费路径

- `TryAddWeaponDefinition` 改为唯一生产入口 `TryAddWeaponRow`。
- `FShooterWeaponInstanceData::DefinitionId` 改为 `WeaponRowName`，同步调整 FastArray 网络序列化。
- Inventory 从表行初始化弹药和 ActorClass。
- WeaponActor、Equipment、FireBehavior 和池化绑定统一改为消费 RowName/表行。
- 无效表、空 RowName、缺失行或非法 ActorClass 必须 fail closed，且不能消费 Pickup。

验证：Build，加 Inventory 授予/拒绝、Equipment、Projectile FireBehavior、Weapon lifecycle 和双客户端 Pickup 定向测试；不跑完整回归。

### C3：删除重复配置层

- 确认生产与测试引用均已迁移后，移除 `UShooterWeaponDefinition`、DefinitionId 解析代码和 AssetManager 扫描配置。
- 通过 Unreal Editor 删除无引用的 `WD_*` 资产并 Fix Up Redirectors。
- 删除一次性 Definition 迁移工具；移除武器蓝图 CDO 中已由表驱动的重复字段。
- 当前四个 Weapon 蓝图先保留为 `WeaponActorClass` 候选；只有确认无结构/逻辑差异后，才另行合并为一个通用蓝图，不塞入本次纠偏。

验证：Build，资产引用审计，以及受影响测试集；不跑完整回归。

### C4：纠偏收口

- 运行一次七阶段完整回归，并审计 Summary 与关键日志。
- 验证 Dedicated Server + 2 Clients：不同玩家可在重生前后拾取同一 Pickup；各武器授予、立即装备、开火、换弹、切枪、死亡清理和池复用正常。
- 为本纠偏建立开发记录，与最终代码/资产改动同提交。
- 通过后再回到原计划 B3，后续文档与测试统一使用 RowName 术语。

## 7. 完成标准

- 新增或调整一把普通武器时，大部分工作只需新增/编辑 `DT_WeaponData` 一行并让 Pickup 选择该行。
- 生产路径不再出现 `UShooterWeaponDefinition`、`WD_*`、`FPrimaryAssetId DefinitionId` 或按武器 Definition 的 AssetManager 扫描。
- 可表格化数据只有一个权威来源，Weapon 蓝图 CDO 不再覆盖同名配置。
- RowName 丢失、表行非法或资源缺失时明确拒绝授予，Pickup 保持可用。
- `InstanceId` 继续可靠关联弹药、装备事务、WeaponActor 与池化生命周期，但不暴露为武器配置流程。
- C0～C3 仅做定向验证；C4 只运行一次完整回归。

## 8. 外部依据与本项目取舍

UE 5.6 官方 Data Driven Gameplay 文档说明，DataTable 行由继承 `FTableRowBase` 的结构定义，字段可使用有效的 UObject 属性（包括资产引用），并可通过 `FDataTableRowHandle` 选择表和行；这足以支撑当前项目的一行完整武器配置。参考：<https://dev.epicgames.com/documentation/en-us/unreal-engine/data-driven-gameplay-elements-in-unreal-engine?application_version=5.6>。

UE Asset Manager/Primary Asset 适合需要显式主资产身份、扫描和加载规则的内容。当前项目只有一张正式武器表和少量武器类型，没有独立 Definition 资产生命周期需求，因此本计划不继续承担这层复杂度。参考：<https://dev.epicgames.com/documentation/en-us/unreal-engine/asset-management-in-unreal-engine?application_version=5.6>。

本取舍不是认为 DataAsset 架构普遍错误，而是针对当前 Demo 规模优先保证：一处配置、一次选择、清晰复制、可验证迁移。
