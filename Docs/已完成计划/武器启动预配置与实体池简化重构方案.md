## 2. 目标与最简结论

把当前运行时模型从：

```text
Pickup.RowHandle / RowName
→ Inventory.TryAddWeaponRow
→ 拾取时查表并创建 WeaponInstanceId
→ Pool.Acquire(ActorClass)
→ WeaponActor 绑定 InstanceId / RowName
```

改为：

```text
世界开始：DT_WeaponData → 不可变配置快照 → 按 WeaponId 预创建武器池

运行时：Pickup.WeaponId
→ 从对应池取得已经配置好的 WeaponActor
→ Inventory 保存 WeaponActor + SlotIndex
→ Equipment 直接装备 WeaponActor
```

最终只保留四个运行时概念：

| 概念 | 表达方式 | 职责 |
|---|---|---|
| 武器种类 | `FName WeaponId` | Pickup 选择、配置快照键、对象池分桶、Inventory 判重 |
| 具体武器 | `AShooterWeapon*` | 当前对局中一件真实存在的池化武器实体 |
| 背包位置 | `int32 SlotIndex` | 切枪顺序与容量约束 |
| 当前装备 | `AShooterWeapon* CurrentWeaponActor` | Equipment 唯一装备权威 |

删除运行时的 `WeaponType / InstanceId / BoundInstanceId / ActiveWeaponInstanceId /
WeaponRowName` 多重身份。当前对局不需要给每个池 Actor 再生成一份自定义 GUID；
需要查询某一件具体武器时直接使用 Actor 引用，UE 网络层负责复制 Actor 身份。

## 3. 核心设计判断

### 3.1 DataTable 只负责开局输入

`/Game/Shooter/Data/DT_WeaponData` 继续是一张完整武器配置表，但职责改为：

```text
编辑器配置源
→ World 启动时完整读取、校验并复制
→ 形成当前 World / 对局不可变的 RuntimeConfig
→ 运行时不再访问 UDataTable 或缓存 Row 指针
```

表的 RowName 只在启动导入边界转换为 `WeaponId`，不再泄漏到 Inventory、Equipment、
WeaponActor 授予 API 或 GAS Ability。无需在行结构中增加一列重复的 `WeaponId`。

允许的唯一例外是编辑器预览：Pickup 为了在编辑器视口显示预览 Mesh，可以通过 Editor-only
校验/预览入口读取表；该入口不得参与打包后的授予逻辑。

### 3.2 池中的 WeaponActor 就是武器实例

本方案不再把 WeaponActor 定义为“可替换的表现外壳”。每个预创建 Actor 在当前 World 生命周期内：

- 创建时确定 `WeaponId`，之后永不改变；
- 创建时应用一次该 WeaponId 的完整静态配置；
- 在不同玩家之间可以被释放和再次租用，但始终属于同一种武器；
- 当前弹匣、备弹、Owner、开火计时器和装备状态属于 Actor 的可变运行时状态；
- Release 清空租用状态并恢复该武器的初始弹药，静态配置不重复应用。

由此不再需要“逻辑 WeaponInstance 与世界 Actor 的绑定关系”，也不再需要每次 Acquire 生成新的
`InstanceId` 来关联二者。

### 3.3 不再提前提交再回滚

授予顺序固定为：

```text
1. 校验服务器权威、角色存活、非换弹状态
2. 校验 Inventory 不含 WeaponId、存在空 Slot
3. 从 WeaponId 对应池 Acquire
4. 为 Actor 设置 Owner / Instigator 并复位租用状态
5. 向 Inventory 提交 WeaponActor + SlotIndex
6. 由 Equipment 装备该 Actor
7. 成功后消费 Pickup
```

步骤 1～3 失败时 Inventory 尚未发生变化，因此没有正常业务回滚。
步骤 4～6 若因代码错误意外失败，只执行纵深防御：移除未完成 Entry 并把 Actor Release 回池；
这不是正常授予流程的一部分。

### 3.4 启动预热，耗尽时从快照弹性 Spawn

每个武器配置行新增：

```text
InitialPoolSize
```

服务器在 World 开始时为每个 WeaponId 创建初始数量的 Actor。运行时该 Bucket 没有可用 Actor 时：

- 直接使用启动时已经冻结的 `RuntimeConfig` Spawn 一个同 WeaponId Actor；
- 对新 Actor 写入 WeaponId、应用静态配置并完成租用复位；
- Spawn 成功后直接返回 `AShooterWeapon*`，不生成任何额外对象 ID；
- Spawn 失败返回 `AcquireFailed`，Inventory 尚未提交，Pickup 保持可用；
- 后续 Release 时把扩容 Actor 留在该 WeaponId Bucket 复用。

首轮不引入最大容量、自动缩容、跨 World 池或复杂容量算法；`InitialPoolSize` 只控制启动预热数量，
不限制当前 World 后续实际增长数量。

## 4. 目标运行时结构

### 4.1 World 级武器运行时子系统

新增或由现有池实现收敛为一个武器专用的 `UShooterWeaponRuntimeSubsystem : UWorldSubsystem`：

```text
UShooterWeaponRuntimeSubsystem
└─ TMap<FName, FShooterWeaponRuntimeBucket> Buckets
   └─ FShooterWeaponRuntimeBucket
      ├─ WeaponId
      ├─ FShooterWeaponConfigRow RuntimeConfig
      ├─ AvailableActors
      └─ LeasedActors
```

只提供必要接口：

```text
InitializeWeaponRuntime()
AcquireWeapon(WeaponId, Owner, Instigator)
ReleaseWeapon(WeaponActor)
FindRuntimeConfig(WeaponId)
HasWeaponId(WeaponId)
GetAvailableCount(WeaponId)       // 测试与诊断
GetLeasedCount(WeaponId)          // 测试与诊断
```

`AcquireWeapon` 的成功返回值就是最终供 Inventory、Equipment 与 GAS 使用的 `AShooterWeapon*`；
不返回池句柄、InstanceId 或中间包装对象。

取消并删除当前 `UShooterActorPoolSubsystem` 与 `IShooterPoolableActor` 通用池抽象；武器池的
Available/Leased 容器、Spawn、Acquire、Release 和诊断全部归入 `UShooterWeaponRuntimeSubsystem`。
Projectile 继续按当前路径生成/销毁；只有出现第二个真实池化消费者时，才重新评估公共池基础层。

### 4.2 初始化时序

`UWorldSubsystem::OnWorldBeginPlay` 执行：

```text
所有端：
1. 加载 DT_WeaponData 一次
2. 校验 RowStruct 与所有正式行
3. 把每行复制进 RuntimeConfig Map

服务器：
4. 按 InitialPoolSize 预创建复制型 WeaponActor
5. 写入稳定 WeaponId
6. 应用静态配置一次
7. 执行 Release 状态初始化并放入对应 Bucket
8. Bucket 后续耗尽时仍只使用这里冻结的 RuntimeConfig 扩容 Spawn

客户端：
4. 不自主创建权威 WeaponActor
5. 接收服务器预创建 Actor
6. Actor 根据复制到达的 WeaponId，从本地 RuntimeConfig 快照应用相同静态表现配置
```

客户端步骤 6 是内存快照查询，不是 DataTable 查询。`WeaponId` 对 Actor 来说是创建后不变的初始复制数据。

### 4.3 WeaponActor

目标字段：

```text
静态/创建后不变
├─ WeaponId
├─ MagazineSize
├─ Fire / Timing / Attack 参数
├─ Mesh / Anim / FX / Audio
└─ FireBehaviorInstance

运行时可变
├─ MagazineAmmo
├─ ReserveAmmo
├─ Owner / Instigator
├─ LifecycleState
├─ Timer / Delegate
└─ Firing / Reload / Equip 状态
```

移除：

- `BoundInstanceId` 及其 RepNotify；
- `WeaponRowName` 的运行时查表职责；
- `SetInstanceBinding`；
- 从 Owner Inventory 反向查找配置或弹药；
- `CurrentBullets` 兼容镜像命名，统一为 `MagazineAmmo`。

保留并简化生命周期：

```text
InPool → Holstered → Equipping → Equipped → Holstered → InPool
```

### 4.4 Inventory

`FShooterWeaponInstanceData` 与其 Entry 改为最小 Actor Entry：

```text
FShooterInventoryWeaponEntry
├─ TObjectPtr<AShooterWeapon> Weapon
└─ int32 SlotIndex
```

Inventory 职责：

- OwnerOnly 复制所持 WeaponActor 与 Slot；
- 按 `Weapon->GetWeaponId()` 判断是否已有同一种武器；
- 按 Slot 查询和遍历下一把武器；
- Add / Remove / Clear 时维护 Actor 引用；
- Remove / Clear 先通知 Equipment 清空，再把 Actor Release 回池。

Inventory 不再：

- 读取 DataTable；
- 生成 GUID；
- 保存弹药；
- 维护 `InstanceId → WeaponActor` 映射；
- 转发 Equipment 的当前武器身份。

背包槽位首版最多 3 个，所有查询使用短数组线性扫描，不额外维护重复 Map。

### 4.5 Equipment

Equipment 只保留：

```text
CurrentWeaponActor : AShooterWeapon*
```

- `CurrentWeaponActor` 继续复制给所有观察者；
- 删除 `ActiveWeaponInstanceId`；
- `EquipWeapon` 改为接收经过 Inventory 验证的 Actor；
- 切枪候选由 Inventory 按 Slot 返回 Actor；
- Equipment 继续负责装备事务、表现收敛与装备变化事件。

### 4.6 Pickup

Pickup 只保存：

```text
WeaponId
RespawnTime
bPickupAvailable
```

运行时不再保存 `FDataTableRowHandle`，也不调用 `GetRow()`。

```text
Authority Overlap
→ Inventory.HasWeaponId(WeaponId)
→ WeaponRuntimeSubsystem.AcquireWeapon(WeaponId)
→ Inventory.AddWeapon(Actor)
→ Equipment.EquipWeapon(Actor)
→ 成功后隐藏并进入 Respawn
```

### 4.7 GAS

三条 Ability 都直接围绕 `CurrentWeaponActor` 工作：

```text
GA_Fire   → CurrentWeaponActor.TryFire()
GA_Reload → CurrentWeaponActor.TryReload()
GA_Equip  → Inventory.FindNextWeapon(CurrentActor) → Equipment.EquipWeapon(TargetActor)
```

服务器在每次提交前验证：

- Actor 仍在该角色 Inventory；
- `Actor->GetOwner() == Character`；
- Equipment 的 Current Actor 与 Ability 目标一致；
- Actor 不处于 `InPool`。

这些校验用于拒绝旧客户端请求作用到已经归还并租给另一名玩家的池 Actor。

## 5. 网络边界

目标复制关系：

| 字段 | 范围 | 说明 |
|---|---|---|
| Inventory Entries（Actor + Slot） | OwnerOnly | 完整背包只对拥有者可见 |
| Equipment.CurrentWeaponActor | 所有观察者 | 第三人称当前持枪表现 |
| WeaponActor.WeaponId | 初始复制/所有观察者 | 客户端从启动快照恢复静态表现 |
| WeaponActor.MagazineAmmo / ReserveAmmo | OwnerOnly | HUD 与本地表现 |
| WeaponActor.Owner | UE Actor Owner 复制 | 租用归属 |

Actor 引用和 `WeaponId` 的 RepNotify 到达顺序不作假设；所有表现入口必须幂等，任一字段晚到后均能再次收敛。

首轮保持当前“隐藏池 Actor 仍存在于 World”边界，不把 Net Dormancy 与身份重构混在同一批。
若池规模实测造成复制压力，再单独增加 `DORM_DormantAll`，并严格在修改复制属性前唤醒 Actor。

## 6. 配置与失败规则

启动阶段每行必须满足：

- WeaponId（RowName）非空且唯一；
- `WeaponActorClass` 是可生成的 `AShooterWeapon` 子类；
- `InitialPoolSize > 0`；
- 弹匣、备弹、射速、时序等现有合法性约束通过；
- 正式 WeaponId 不共享一个会导致池配置混淆的错误实现资产；
- 所有软引用资源能够解析。

失败策略：

| 失败 | 行为 |
|---|---|
| 表缺失、结构错误 | RuntimeSubsystem 初始化失败；正式测试直接失败 |
| 单行非法 | 该 WeaponId 不建立 Bucket；输出一次 Error |
| 预创建数量不足 | 该 WeaponId 初始化失败，不允许半可用池 |
| 未知 WeaponId | Pickup 不消费，返回 InvalidWeaponId |
| 可用池为空 | 从 RuntimeConfig Spawn 一个 Actor 并直接返回引用 |
| 弹性 Spawn 失败 | Pickup 不消费，返回 AcquireFailed |
| 重复 WeaponId | Pickup 不消费，返回 DuplicateWeapon |
| Slot 满 | Pickup 不消费，返回 SlotFull |

## 7. 与当前实现的差异

| 当前 | 目标 |
|---|---|
| `ShooterWeaponTable` 在运行时解析表 | 只在 World 启动时生成快照 |
| Pickup 保存 RowHandle | Pickup 只保存 WeaponId |
| Inventory.TryAddWeaponRow | Inventory 接收已经 Acquire 的 Actor |
| 拾取时创建 InstanceId | 不创建 InstanceId |
| Inventory 保存 Ammo | WeaponActor 保存 Ammo |
| 通用 ActorPool 按 ActorClass 分池 | 删除通用池，WeaponRuntimeSubsystem 按 WeaponId 管理预热与弹性扩容 |
| Actor 每次绑定 RowName/InstanceId | Actor 创建时永久确定 WeaponId/静态配置 |
| Equipment 保存 Actor + ActiveInstanceId | Equipment 只保存 Actor |
| Acquire 失败回滚已写入的 Instance | Acquire 成功后才提交 Inventory |
| 玩家与 NPC 两套弹药权威 | NPC 与玩家都租用预配置 WeaponActor |

NPC 是否在本次迁移中接入同一武器池是正式验收门槛：不再保留无 Instance 的旧兼容分支，
因为目标模型本身已经不需要 Instance。

## 10. 完成标准

- 打包运行期间只有启动阶段访问 `DT_WeaponData`；Pickup、Inventory、Equipment、WeaponActor 和 GAS
  均不调用 DataTable API；
- 每个正式 WeaponId 在 World 开始时具有配置完成的初始 Actor 池；
- 可用池耗尽时只从启动快照 Spawn，成功后直接返回 Actor 引用，失败不提交 Inventory；
- Pickup 只配置 WeaponId，未知、重复、Slot 满或 Spawn 失败均不消费；
- Inventory 数据只包含 Actor 引用和 Slot，不存在 InstanceId/RowName；
- Equipment 只以 CurrentWeaponActor 表达当前装备；
- 玩家与 NPC 共用 WeaponActor 弹药和池生命周期；
- 旧 Owner 的延迟事件或旧客户端请求不能影响已经租给新 Owner 的 Actor；
- 死亡、断线、移除后 Inventory/Equipment 无引用，Actor 全部回到正确 WeaponId Bucket；
- 七阶段回归通过，Automation 无 Failed/NotRun，网络检查 `DirtyPooled=0`、`Orphans=0`；
- P1 文档改为依赖 `WeaponId / WeaponActor / SlotIndex / CurrentWeaponActor`，不再依赖 InstanceId。

## 11. 明确非目标

- 不实现 Local Predicted Fire；
- 不实现 Projectile Pool；
- 不实现跨 World 或跨对局武器持久身份；
- 不实现武器交易、耐久、随机词条、配件实例；
- 不为池 Actor 分配自定义 GUID；
- 不保留当前通用 ActorPool 或为未来消费者预留公共池接口；
- 不实现池最大容量、自动缩容或运行时重新读取 DataTable；
- 不引入 WeaponDefinition、PrimaryAsset、DataRegistry 或新的配置资产层；
- 不在身份迁移同时引入 Net Dormancy、Replication Graph 或 Iris 改造。

## 12. 外部依据与本地 UE5.6 核对

- UE 官方 Data Driven Gameplay 文档说明 DataTable 是集中维护静态数据的配置源，行通过 RowName/Handle
  访问；同时提示返回的行指针不应跨局部作用域长期缓存。本方案因此在启动时复制行值形成运行时快照，
  不保存 Row 指针：
  <https://dev.epicgames.com/documentation/en-us/unreal-engine/data-driven-gameplay-elements-in-unreal-engine?application_version=5.6>。
- UE 官方 `UWorldSubsystem` 文档说明 `OnWorldBeginPlay` 在 World 准备开始玩法、Actor BeginPlay 前调用；
  本地 UE5.6 `Engine/Source/Runtime/Engine/Public/Subsystems/WorldSubsystem.h` 也存在相同虚函数，
  适合作为配置冻结与服务器池预创建边界：
  <https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UWorldSubsystem>。
- UE 官方网络文档确认 Actor 是网络复制的主要实体，因此当前对局内 Inventory 可以复制 Actor 引用，
  不必再叠加一套自定义实例 GUID：
  <https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine>。
- UE 官方 Dormancy 文档要求休眠 Actor 在修改复制属性前先唤醒；为了控制变量，本方案首轮不把 Dormancy
  与身份重构混做，池规模扩大后再独立测量和实施：
  <https://dev.epicgames.com/documentation/en-us/unreal-engine/actor-network-dormancy-in-unreal-engine>。

## 13. 已确认策略

用户已确认以下决策，不再作为后续审批分支：

1. 删除 `UShooterActorPoolSubsystem` / `IShooterPoolableActor` 通用对象池，不保留未来 Projectile
   消费者的预留抽象；
2. 每个 WeaponId 在启动时按 `InitialPoolSize` 预热；可用池耗尽时从已冻结 RuntimeConfig
   即时 Spawn，禁止重新查询 DataTable；
3. Acquire 成功后直接返回 `AShooterWeapon*`，Inventory、Equipment 与 GAS 全程使用对象引用；
4. 不增加 InstanceId、PoolHandle、WeaponObjectId 或其他中间身份。
