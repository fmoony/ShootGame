# Shooter 模板多人网络改造计划

## 目标

在保留 UE Shooter 模板原有结构的前提下，用最小改动逐步理解并实现：

```text
客户端输入 → Server RPC → 服务器验证和执行
                         ↓
              复制权威状态或广播表现
                         ↓
                 所有客户端得到结果
```

当前阶段以学习网络所有权、属性复制、RPC 和服务器权威为主，暂不引入 Gameplay Ability System、复杂预测、背包框架或大型重构。

## 当前完成状态

截至 2026-08-13，本计划的服务器权威多人网络主闭环已经完成：

| 阶段 | 状态 | 已形成的闭环 |
| --- | --- | --- |
| 一：拾取与装备 | 已完成 | 服务器生成武器，复制当前武器，客户端幂等刷新附着与 AnimBP |
| 二：权威开火 | 已完成 | 客户端输入经 Server RPC，服务器校验并开火，Multicast 同步动画、Niagara 与声音 |
| 三：弹丸与伤害 | 已完成 | 服务器生成和判定弹丸；复制移动、生命、死亡及命中表现 |
| 四：切枪与弹药 | 已完成 | 服务器切枪；当前武器复制；弹药仅复制给拥有者 |
| 五：比赛与玩家状态 | 已完成 | 队伍分数进入 GameState，队伍/击杀/死亡进入 PlayerState，Widget 归本地 Controller |
| 六：动画网络表现 | 已完成 | 第一人称仅本地；第三人称使用移动复制和 Character 远程视角数据驱动俯仰 |
| 七：验证矩阵 | 已完成 | 编译、Automation、Standalone、Listen、Dedicated、延迟丢包、断线清理均自动验收 |

基础网络实验代码（`NetCounter`、Reliable/Unreliable、Client/Multicast RPC）仍保留用于学习，但 Shooter 实际玩法不再依赖这些实验变量。

### 当前明确边界

- 仍采用模板的“弹匣打空后自动补满”规则，尚未实现换弹流程、备弹池和换弹 Montage。
- 没有客户端预测、回滚、服务器倒带或延迟补偿；高延迟下保证权威正确，不保证竞技射击手感。
- 自动化使用 `NullRHI`，可以验证资产、调用路径、复制状态和远端 Montage 状态，但 Niagara、声音衰减、HUD 排版和主观观感仍需带渲染 PIE 人工验收。
- 弹道自动化验证服务器使用远端 `ControlRotation` 且弹丸不会射入朝向后半球；近处遮挡会使枪口到命中点的方向明显偏离准星前向，因此像素级准星重合仍属于带渲染人工验收，不以固定 `AimDot` 代替。
- 蓝图 `BP_ShooterCharacter` 当前配置的 `MaxHP` 约为 `999999995904`，自动化能验证复制和死亡闭环，但该数值明显偏离正常玩法，后续应作为独立资产配置调整，不与网络代码混改。
- 同一 Pickup 的双人同时争抢、长时间全自动射击和切枪/死亡的同帧竞态尚未形成专门的确定性自动用例，保留为人工回归或后续测试扩展项。

## 实施原则

1. 服务器产生武器、弹丸、伤害、生命和得分等权威结果。
2. 客户端只提交输入意图，不直接决定命中或弹药结果。
3. `ReplicatedUsing` 用于持续状态；RPC 用于短暂事件。
4. 第一版先保证正确，不立即加入客户端预测和延迟补偿。
5. 每完成一个阶段先运行多进程自动化矩阵，再对 Niagara、声音和 HUD 做带渲染 PIE 观察。

## 阶段一：服务器权威拾取和装备（已完成）

这是下一步最适合完成的最小闭环。

### 改动目标

- Pickup 的重叠判定只在服务器处理。
- `AddWeaponClass` 只允许服务器生成武器。
- 服务器设置武器的 Owner 和 Instigator。
- 在角色上复制 `CurrentWeapon`。
- 通过 `OnRep_CurrentWeapon` 在客户端完成：
  - Mesh 附着。
  - 第一/第三人称 AnimBP 切换。
  - 当前武器显示状态更新。
- `OwnedWeapons` 第一版可只由服务器维护；需要客户端切枪列表时再复制。

### 建议实现顺序

1. 给 `AShooterPickup::OnOverlap` 增加 Authority 检查。
2. 给 `AShooterCharacter::AddWeaponClass` 增加 Authority 检查。
3. 将 `CurrentWeapon` 声明为 `ReplicatedUsing=OnRep_CurrentWeapon`。
4. 在 `GetLifetimeReplicatedProps` 注册 `CurrentWeapon`。
5. 抽取一个服务器和 OnRep 都能调用的 `ApplyCurrentWeapon` 函数。
6. 确认武器附着和 AnimBP 设置可以重复调用而不会产生副作用。

### 验收条件

- 客户端捡起武器后，服务器和两端客户端只存在同一个网络武器 Actor。
- 拾取者能看到第一人称武器。
- 另一名玩家能看到拾取者的第三人称武器。
- 两端角色使用相同的武器类型动画。
- 日志中武器生成只发生在 Authority。

## 阶段二：服务器权威开火（已完成）

### 改动目标

- 输入仍在本地角色中绑定。
- 本地按键调用 `ServerStartFire`，松开调用 `ServerStopFire`。
- 服务器检查：
  - RPC 调用者是否拥有该角色。
  - `CurrentWeapon` 是否有效。
  - 射速冷却是否结束。
  - 弹药是否足够。
- 只有服务器调用武器真正的 `StartFiring`、`StopFiring` 和 `FireProjectile`。

### 瞄准数据

第一版可以让客户端把目标点随开火请求发给服务器，但服务器必须进行基本检查：

- 目标方向与角色/Controller 朝向差异不能异常。
- 目标距离不能超过 `MaxAimDistance`。
- 服务器不能直接相信客户端报告的命中 Actor。

更简单的学习版本也可以由服务器使用角色 Control Rotation 重新计算射线。

### 表现同步

- 第一人称后坐力只对拥有者播放。
- 第三人称开火 Montage、枪口闪光和声音可使用不可靠 Multicast，或复制一个递增的射击序号触发 `OnRep`。
- 不要使用可靠 Multicast 发送高频全自动枪的每一帧状态。

### 验收条件

- 客户端不能在本地绕过服务器直接生成弹丸。
- 服务器和所有客户端观察到一致的射速。
- 远程玩家能够看到开火动画和枪口表现。

### 实际实现记录

- **弹药规则**：服务器维护 `CurrentBullets`，阶段四使用 `COND_OwnerOnly` 复制；仍保留模板的打空自动补满规则。
- **瞄准数据**：服务器使用远端角色同步到服务端的 `ControlRotation` 重新 trace，不接收客户端报告的命中 Actor。多进程用例验证服务器确实生成弹丸且方向位于控制器朝向前半球；`AimDot` 是诊断值，不是必须等于 `1.000` 的精度指标。
- **枪口表现**：服务器每次权威射击调用不可靠 `MulticastPlayFiringFX`；拥有者选择第一人称 Mesh，其余端选择第三人称 Mesh，并在枪口 Socket 播放 Niagara 与附着音效。资产是否配置由 Automation 快速测试覆盖，最终观感仍需渲染验收。
- **后坐力**：维持服务器权威路径，不加入本地预测；NPC 的后坐接口保持空实现。

## 阶段三：弹丸、命中和伤害（已完成）

### 改动目标

- `AShooterProjectile` 开启 Actor 复制和移动复制。
- 弹丸只由服务器生成。
- `NotifyHit`、爆炸范围检测、`ApplyDamage` 和销毁只由服务器决定。
- 客户端只播放命中特效，不修改生命值。
- 将角色 `CurrentHP` 改为 `ReplicatedUsing=OnRep_CurrentHP`。
- 死亡状态由服务器设置并复制。

### 验收条件

- 两名玩家都能看到同一颗弹丸的大致轨迹和销毁时机。
- 同一次命中只扣一次血。
- 客户端无法自行修改其他角色生命。
- 服务器与客户端看到一致的死亡结果。

### 实际实现记录

- `AShooterProjectile` 开启 Actor 与移动复制，客户端关闭碰撞，只观察服务器弹道。
- `NotifyHit`、范围伤害、伤害应用和销毁均有 Authority 边界；命中表现使用不可靠 Multicast。
- `CurrentHP` 与 `bIsDead` 由服务器修改并复制，`OnRep` 负责客户端表现；测试协调器验证部分伤害、致死伤害和一致死亡状态。

## 阶段四：武器切换和弹药（已完成）

### 改动目标

- 切枪输入通过 Server RPC 请求。
- 服务器修改 `CurrentWeapon`。
- 客户端通过 `OnRep_CurrentWeapon` 更新 Mesh、AnimBP 和 HUD。
- `CurrentBullets` 由服务器维护并复制给拥有者。
- 弹药复制优先使用 `COND_OwnerOnly`，避免把不必要的精确弹药数据发送给所有玩家。

### 验收条件

- 客户端切枪后，其他客户端能看到正确的第三人称武器和动画。
- HUD 弹药只显示自己的权威弹药。
- 快速切枪和开火不会留下错误的计时器或隐藏状态。

### 实际实现记录

- 切枪输入通过 `ServerSwitchWeapon` 到达服务器，服务器循环选择 `OwnedWeapons` 并复制 `CurrentWeapon`。
- `CurrentBullets` 仅复制给武器拥有者，非拥有客户端不会得到精确弹药。
- 武器与角色结束生命周期时清理开火计时器；角色离场时服务器显式销毁其 `OwnedWeapons`，避免断线遗留孤儿 Actor。

## 阶段五：GameState、PlayerState 和本地 UI（已完成）

### 职责迁移

| 类型 | 放置内容 |
| --- | --- |
| GameMode | 服务器规则、出生和计分入口 |
| GameState | 所有客户端都要看到的比赛分数和比赛状态 |
| PlayerState | 玩家队伍、个人分数、击杀和死亡 |
| PlayerController | 本地输入、本地 HUD 创建和 UI 更新 |

### 改动目标

- 将 `TeamScores` 从仅服务器存在的 GameMode 迁移到可复制的 GameState。
- 将队伍和个人统计放入 PlayerState。
- 所有 Widget 都由本地 PlayerController 创建。
- 专用服务器永远不访问 Viewport。

### 实际实现记录

- `AShooterGameState` 复制 `TeamScores`；`AShooterPlayerState` 复制 `TeamId`、`Kills`、`Deaths`，并使用内置 Score。
- GameMode 只负责分队、规则与计分入口；死亡时服务器更新击杀者、阵亡者和队伍分数。
- 弹药 HUD 与计分板均由本地 `AShooterPlayerController` 创建和绑定，`OnRep_Pawn` 处理客户端稍后收到 Pawn 的情况。

## 阶段六：动画网络表现（已完成）

### 改动目标

- 第一人称 AnimBP 继续只依赖本地摄像机。
- 第三人称 AnimBP 根据复制后的 CharacterMovement 和当前武器自行更新。
- 远程俯仰优先利用 Character 已有的远程视角数据，再决定是否增加自定义复制变量。
- 开火、换弹和切枪的第三人称 Montage 由网络事件触发。

### 不需要优先复制的动画变量

- `GroundSpeed`
- `Velocity`
- `IsFalling`
- `ShouldMove`
- 本地第一人称 `Aim Target`

这些值能够从已有移动状态或本地摄像机重新计算。

### 实际实现记录

- 第一人称 Mesh 使用 `OnlyOwnerSee`，第三人称 Mesh 使用 `OwnerNoSee`；第一人称 AnimBP 的摄像机逻辑保留 `Is Locally Controlled` 保护。
- 第三人称移动变量继续从复制后的 CharacterMovement 推导，不新增重复复制属性。
- 模拟代理在 `PostNetReceive` 中读取 Character 已有的 `GetBaseAimRotation()`，将远程俯仰写入模板第三人称 AnimBP 的 `PitchN`，避免额外自定义网络变量。
- 第三人称 AnimGraph 的 `Arms` Slot 接收远端开火 Montage；自动化验证两客户端的远端俯仰与 Montage 状态。

## 阶段七：测试矩阵（已完成）

每个阶段至少验证以下模式：

| 模式 | 玩家数 | 重点 |
| --- | ---: | --- |
| Standalone | 1 | 确保原模板功能没有回退 |
| Listen Server | 2 | 主机与远程客户端的所有权差异 |
| Dedicated Server | 2 | 排除本地 UI、摄像机和 Controller 假设 |

建议测试用例：

- 主机拾取，客户端观察。
- 客户端拾取，主机观察。
- 两人同时争抢同一个 Pickup。
- 客户端持续开火并快速松开。
- 开火过程中切枪、死亡或销毁武器。
- 高延迟和丢包条件下检查 Reliable/Unreliable 表现。
- 客户端断开后，武器和计时器是否正确清理。

### 自动化落地

`Scripts/Tests/RunAll.ps1` 当前串联七个阶段：

1. `Build`：编译 `ShootGameEditor Win64 Development`。
2. `Automation`：运行 `ShootGame.*` 资产和配置测试。
3. `Standalone`：独立端加载 Shooter 地图并检查崩溃、`Accessed None` 等标记。
4. `DedicatedNetwork`：专用服务器加两个真实客户端，验证完整网络业务链。
5. `ListenNetwork`：监听服务器加一个远程客户端，验证主机/远端所有权差异。
6. `EmulatedNetwork`：服务端和两客户端施加 `100ms` 延迟与 `2%` 丢包。
7. `DisconnectCleanup`：主动断开客户端并验证没有无效 Owner 的存活武器。

2026-08-13 的完整通过记录位于 `Saved/Automation/Runs/20260813_192958/Summary.json`。该目录属于运行产物，不提交 Git；Agent 必须以每次最新运行结果为准。

## 后续学习入口

本计划定义的第一版多人网络主闭环已经完成。后续不应继续无边界扩张，而应从以下方向中一次选择一个新闭环：

1. 修正 `BP_ShooterCharacter.MaxHP`，补充正常血量、复活和出生保护规则。
2. 实现备弹池、换弹 Server RPC、换弹 Montage 与中断规则。
3. 为同一 Pickup 双人争抢、持续全自动开火、开火中切枪/死亡增加确定性测试。
4. 在带渲染 PIE 中验收 Niagara、声音衰减、HUD 和第一/第三人称观感，并记录资产级问题。
5. 若学习竞技网络，再单独设计客户端预测、延迟补偿与服务器倒带；不要直接塞入当前最小模板闭环。

原则不变：一次只完成一个可验证闭环；代码结果走自动化矩阵，视觉和听觉结果补充人工渲染验收。
